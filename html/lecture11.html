第 11 讲｜Agent 需要什么数据

在传统单轮自然语言处理任务中，“数据”往往意味着一张静态的二维表格：左边一列是输入文本 x，右边一列是标准答案标签 y。然而，当我们构建一个多步调用工具、读写外部状态、与用户多轮交互的 AI Agent 时，静态的 (x, y) 问答对就远远不够了。

如果一个 Agent 在处理“核对上周差旅发票并提交报销单”时失败了，究竟是因为它在第一步搜错了政策文档、在第二步填错了汇率计算参数、还是在第三步遇到工具超时后不知道如何重试？要诊断、优化并评测这样一个动态系统，我们需要捕获并构建专门面向智能体的数据资产。本讲作为“智能体数据工程（Data for Agentic Systems）”单元的开篇，将系统剖析 Agent 数据的三种核心形态——运行轨迹（Traces）、行为示范（Demonstrations）与评价反馈（Feedback），厘清用于系统优化（Optimization）与用于基准评测（Evaluation）的数据边界，并深入探讨如何构建持续自我进化的数据飞轮（Data Flywheels）、开展高质量合成数据生成（Synthetic Data Generation）以及从真实人机交互中采集高价值信号。

学习目标

  • 严格区分运行轨迹（Traces）、示范数据（Demonstrations）与评价反馈（Feedback）三类数据形态的结构、信息密度与工程用途。
  • 掌握优化数据（Optimization Data）与评测数据（Evaluation Data）的隔离原则，防止多跳轨迹与同源会话造成数据泄漏。
  • 掌握构建 AI 工程数据飞轮（Data Flywheel）的闭环流程，理解如何将线上失败轨迹转化为可验证的系统改进。
  • 掌握面向 Agent 的合成数据生成策略与质量控制边界，学会从真实人机交互（澄清、拒绝、中途转向與手动修改）中提取隐式监督信号。

知识讲解

1. 数据的三种形态

Traces

在 Agent 系统中，最基础、最原始的数据形态是运行轨迹（Traces / Trajectories / Rollouts）。一条完整的 Trace 是对一次任务运行过程（Trial）所发生事实的忠实、结构化记录，通常包含：

  1. 初始上下文与配置快照：用户请求、系统提示版本、模型名称与采样参数（Temperature 等）、启用工具列表的 Schema 版本以及环境初始状态标识；
  2. 完整的时间步事件序列（Event Sequence）：每一步的模型内部推理（Thought）、发出的结构化工具调用（Tool Call）、工具实际执行的耗时与返回结果（Observation / Error），以及期间发生的上下文压缩（Compaction）或用户插话事件；
  3. 终止状态与资源账单：终止原因（正常完成、超出轮数、超出预算、连续格式错误或用户取消）、最终环境产出物（Artifacts）以及各步骤的 Token 消耗与延迟明细。

工程认知：Trace 首先是一份客观的诊断与审计证据（Diagnostic Evidence），它回答的是“系统实际上做了什么”。需要注意的是，哪怕一条 Trace 最终碰巧得出了正确答案，它的中间步骤也可能充满了冗余试探、格式错误或侥幸绕过的陷阱——因此，原始成功轨迹并不自动等同于可以直接拿去模仿学习的高质量示范；反过来，最终失败的轨迹也绝非废品，它们恰恰是定位系统短板、构造纠错训练样本的宝矿。

Demonstrations

第二种数据形态是行为示范（Demonstrations）——它表达的是“我们希望 Agent 在给定状态下学会采取的模范行为”。在复合系统与 Agent 中，Demonstration 既可以是：

  • 阶段级示范：如 DSPy 模块中经过评测指标筛选的少样本示例（给定邮件正文 → 输出标准推理链与结构化日程字段）；
  • 完整轨迹示范（Expert Trajectories）：展示如何一步步分解问题、选择工具、根据报错调整查询并最终解决问题的端到端多步序列。

示范数据的来源通常有三条途径：（1）由领域人类专家亲手操作或编写（成本最高但最贴近真实意图）；（2）由参数量更大、能力更强的教师模型（Teacher LLM）生成并通过客观验证器（Verifier）过滤（即拒绝采样自举 Rejection Sampling）；（3）对线上真实运行轨迹进行清洗、剪枝（剪掉走弯路的无效重试步骤）与重写修正后沉淀而来。在使用任何示范数据前，都必须明确记录其生成来源与过滤条件。

Feedback

第三种数据形态是评价反馈（Feedback）——它对某一条完整轨迹或某一步具体动作的好坏给出价值判断。按照信息粒度从粗到细，Feedback 可以分为四个层次：

反馈类型数据形式信息量与定位能力典型应用场景
1. 二元成败信号（Binary Outcome）最终通过 / 失败（$0 / 1$，如单元测试是否跑通）最客观可靠，但属于稀疏末端信号，无法直接指出长轨迹中哪一步出了错RLVR（可验证强化学习）、端到端基准评测
2. 标量评分与多维量表（Scalar / Rubric Scores）按多个评价维度打分（如事实性、合规性、简洁度）能够区分“格式错”、“事实错”还是“违反安全策略”LLM-as-Judge 自动化评估、MIPROv2 优化
3. 成对偏好比较（Pairwise Preference）同一任务下两条轨迹 (ywin, ylose) 的优劣排序比绝对打分更容易达成标注一致性RLHF / DPO 偏好对齐、A/B 策略对比
4. 自然语言批评与过程纠偏（Natural Language Critique / Step-level Feedback）明确指出“第 3 步调用 read_doc 时选错了已作废的旧文档 ID”信息密度最高，直接完成局部信用分配（Credit Assignment）Reflexion、TextGrad、GEPA 反思式提示演化

2. 数据用途与循环

Optimization vs evaluation

收集到 Traces、Demonstrations 和 Feedback 之后，第一条不可触碰的工程红线是：用于优化系统的数据（Optimization Data）与用于最终评测的数据（Evaluation Data）必须严格物理隔离。

  • 优化数据（Train / Dev）：允许被提示优化器（如 MIPROv2、GEPA）用来挑选少样本示例、被工程师用来观察错误模式修改提示词，或者被用来微调模型权重。
  • 评测数据（Held-out Test）：用于客观检验系统在从未见过的任务上的泛化表现。

在 Agent 场景中，切分数据集时极易发生隐蔽的关联泄漏（Correlated Leakage）：如果仅仅把按时间收集的几百条运行轨迹随机打乱按 8:2 切分，同一个用户在同一个项目会话中的前两轮可能分到了训练集，后一轮分到了测试集；或者同一份底层代码仓库、同一批合成邮件模板衍生出的变体同时出现在了两边。因此，Agent 数据的划分必须按独立的任务族（Task Family）、独立的用户会话（Session）、独立的环境实例或时间窗口进行整组切分（Group Split）。

Data flywheel

在真实生产环境中，一个优秀的 Agent 系统不是靠上线前一次性攒够所有数据建成的，而是依靠持续运转的 AI 工程数据飞轮（Data Flywheel, Shankar, 2024） 迭代演进的。一个标准的数据飞轮包含五个紧密咬合的齿轮：

  1. 上线运行与全量采集（Deploy & Log）：保存每一次线上运行的完整 Trace、环境版本与用户后续动作；
  2. 自动化监控与失败采样（Monitor & Sample Failures）：通过确定性规则（如工具报错、超长循环、用户拒绝审批）与轻量级评估器，从海量日常日志中自动捞出高价值的失败或异常轨迹；
  3. 错误归因与数据转化（Critique & Curate）：分析失败根因，将高频新故障转化为两份资产——一份加入回归评估集（Evaluation Suite）以防止未来复发，另一份修正为正确的示范或反例反馈（Demonstrations / Feedback）放入优化训练集；
  4. 系统迭代优化（Optimize System / Prompts / Weights）：利用扩充后的优化数据更新提示词、工具描述、检索索引或微调模型；
  5. 独立门禁验收（Gate on Held-out Evals）：在独立评测集上验证新版系统确实解决了目标问题且未引起存量能力退化后，发布上线开启下一轮循环。

飞轮防偏原则：数据飞轮转得越快，越要警惕评估器偏差的自我强化（Validator Bias Amplification）。如果负责在飞轮中自动筛选“好轨迹”的裁判模型本身偏爱冗长啰嗦的回答，飞轮转上几圈后，整个系统就会彻底退化为废话制造机。因此飞轮必须定期引入人工抽检校准。

Synthetic data generation

在冷启动阶段或面对罕见的长尾边界场景（如恶意提示注入、极端格式错误、复杂多跳推理）时，真实用户数据往往严重不足。此时，合成数据生成（Synthetic Data Generation, Tan et al., 2024） 是扩充训练与测试覆盖面的核心手段。

要防止合成数据沦为“同质化垃圾数据的堆砌”，工程上需遵循三步闭环：种子多样性注入（Seed & Persona Diversity）→ 生成过程受控执行（Grounded Execution）→ 严格验证过滤（Verification & Deduplication）。例如：

  • 不要让大模型凭空编造一段“问题 + 答案”，而是先给定真实的公司文档库或数据库表，从真实文档中的具体段落反向合成需要单跳或多跳才能回答的问题（这样天然自带金标准答案与正确引用 ID）；
  • 注入不同的用户画像（急躁的高管、表述模糊的新员工、试图越权的攻击者）与不同的环境扰动（工具偶尔超时、搜索返回近似干扰项）；
  • 强制用确定性代码或独立验证器检查合成出的轨迹是否真正跑通，并对问题文本与操作序列做语义去重。

Human–agent interaction data

最后，当 Agent 真正与人类协同工作时，人机交互过程本身（Human-Agent Interaction）蕴含着比显式“点赞/点踩”丰富得多的隐式黄金信号：

  • 澄清追问（Clarifications）：当用户不得不连续追问两遍来解释自己的意图时，说明 Agent 缺乏主动识别歧义并调用 ask_user 的能力；
  • 审批拒绝与中途打断（Rejections & Steering）：当用户在确认模式（Confirm Mode）下拒绝了 Agent 提议的 run_terminal 命令，或者在 Agent 执行半途发送新消息强行纠正方向时，这直接标出了系统的安全或理解偏差边界；
  • 采纳后的手动编辑（Post-generation Edits）：当 Agent 生成了一封邮件草稿或一段代码补丁，用户在发送或提交前亲手修改了其中三行——对比 Agent 原始产出 与 用户最终提交版本 的 Diff（差异），就是最精准、零标注成本的天然监督示范（Demonstration）！

在采集和利用人机交互数据时，还必须在架构层做好敏感隐私字段脱敏（PII Redaction）并支持用户删除权，确保数据飞轮在安全合规的轨道上运转。

动手练习

  1. 设计结构化 Trace Schema 与三类数据提取：针对第 05 讲的“邮件提取日程并写入日历”任务，设计一份 JSON Schema 来保存单次运行的完整 Trace。手工或用脚本构造 3 条成功记录与 3 条典型失败记录（如漏算相对日期、误将闲聊邮件写入日历、日历服务连接超时重试），并说明如何从中分别提取出：（a）可用于 Few-shot 的 Demonstration；（b）可用于 GEPA 反思的 Feedback；（c）仅供基础设施排查的诊断日志。
  2. 防泄漏数据集切分设计：假设你收集了某企业 10 名员工在过去一个月内使用内部助手产生的 500 条跨会话交互轨迹。请设计一套 train / dev / test 切分方案，说明为什么不能按单条轨迹随机打乱切分，并给出按用户、按项目主题或按时间切片的具体规则与优劣对比。
