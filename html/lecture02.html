第 02 讲｜面向构建者的大语言模型

构建 AI Agent 的工程师处于整个大模型技术栈的最顶层，但这并不意味着我们可以把底层的语言模型当成一个无所不能的“魔法黑盒”。在实际工程中，为什么你的 Agent 会在长对话后突然遗忘早期的系统指令？为什么工具调用的参数偶尔会漏掉右括号？为什么首次响应延迟（TTFT）和流式生成速度会有数量级的差异？为什么有些模型擅长长文档大海捞针，有些模型却更擅长多步工具调用？

要回答并解决这些工程问题，构建者必须透彻理解现代大语言模型（LLMs）的内部工作机制。本讲将从自回归概率解码出发，深入拆解 Decoder-only Transformer 的计算数据流、注意力机制的复杂度瓶颈与线性化变体、从预训练到强化学习的完整训练管线，以及推理加速、结构化输出约束与上下文工程（Context Engineering）的核心方法。

学习目标

  • 从条件概率链式法则理解自回归语言模型，掌握 Greedy、Top-k、Top-p、Temperature 缩放与 Beam Search 等解码策略的任务权衡。
  • 完整推导 Decoder-only Transformer 的内部数据流，对比标准全注意力（Full Attention）、线性注意力（Linear Attention）与混合注意力（Hybrid Attention）在训练并行度与推理状态空间上的差异。
  • 理解从预训练（Pretraining）、中期训练（Mid-training）、指令微调（SFT）到偏好对齐（RLHF）与可验证奖励强化学习（RLVR）的模型演进脉络。
  • 掌握 GPU 算力与显存带宽瓶颈、KV Cache 复用、投机解码（Speculative Decoding）、测试时计算扩展（Test-time Scaling）、受限解码（Constrained Decoding）以及长上下文工程的实践原则。

知识讲解

1. 语言模型与解码

构建者的三层视角

现代大模型技术栈由下至上可以分为三层：

  1. 模型工程层（LLM Engineering）：关注分布式算力、Transformer 架构改进、GPU 算子（Kernels）、缩放定律（Scaling Laws）、分词器（Tokenizer）与预训练/后训练基础设施（如 CS336 所涵盖的范畴）。
  2. 模型适配层（LLM Adaptation）：关注指令微调（Finetuning）、知识蒸馏（Distillation）、上下文学习（In-Context Learning）、低秩适配（LoRA）以及基于人类反馈的强化学习（RLHF/DPO，如 CS224N 所涵盖的范畴）。
  3. 系统应用层（LLM Applications）：关注如何将模型构建为可靠的检索增强系统（RAG）、工具调用流水线、多智能体系统与主动式 Agent（即本课程 CS329Z 的核心范畴）。

尽管我们工作在最顶层，但底层的架构决策直接决定了上层系统的能力边界、成本结构与故障模式。

序列概率与自回归

从数学本质上看，语言模型是一个对词元序列（Token Sequence）x1, x2, …, xn 赋予联合概率分布的系统。根据概率链式法则，整个序列的联合概率等于每个位置在给定前序上下文条件下生成当前 Token 的条件概率之积：

P(x1, x2, …, xn) = ∏t=1n P(xt \mid x1, …, xt-1)

例如，对于句子 "The class was about agents ."，模型依次计算 P(The) = 0.0377、P(class \mid The) = 0.0001、P(was \mid The, class) = 0.0344 … 并相乘得到整句概率。由于大量小于 $1$ 的浮点数连乘极易导致数值下溢（Underflow），在实际计算与训练中，我们总是对其取对数，将连乘转化为对数概率之和（Sum of Log-Probabilities）。

在机器学习分类中，判别式模型（Discriminative Models，如逻辑回归、SVM）只学习区分不同类别的决策边界 P(y \mid x)；而建模序列分布的语言模型属于生成式模型（Generative Models）——这意味着我们可以通过逐个采样下一词元（Next-token Sampling），让模型自回归（Autoregressively）地生成全新的文本：每生成一个新 Token，就将其追加到输入序列末尾，作为预测下一个 Token 的条件。

Greedy、sampling、top-k、top-p

当模型在时刻 t 输出词表上所有候选 Token 的概率分布后，我们该如何选出下一个词？不同的解码策略（Decoding Strategies）对应着截然不同的系统行为：

  • 贪心解码（Greedy Decoding）：每一步永远选择条件概率最高的那个 Token（例如在 "The class was about" 后直接取概率最高的 "to"，再取 "be"）。这种方法完全确定，但每一步的局部最优未必构成全局最优序列，且容易陷入重复循环。
  • 随机采样（Pure Sampling）：完全按照词表概率分布随机抽取。虽然增加了多样性，但词表尾部成千上万个极低概率的荒谬词元加起来仍有一定概率被抽中，容易导致胡言乱语。
  • Top-k 采样：仅保留概率最高的前 k 个候选词元，将其余词元概率置零并重新归一化后再采样。它的局限在于 k 是固定常数——当模型非常确信（第一名概率高达 $0.95$）时，Top-k 仍会把后面不靠谱的候选纳入；而当分布非常平坦（几十个词都很合理）时，固定的 k 又会切掉合理的表达。
  • 核采样（Nucleus / Top-p Sampling）：按概率从高到低累加候选词，一旦累计概率达到阈值 p（如 p=0.9）就截断后续词元。这样候选集合的大小会根据模型在当前步的不确定性动态伸缩。

Temperature 的作用与概率缩放

除了截断候选集，我们还可以通过温度参数（Temperature, T）在进入 Softmax 归一化之前调节分布的陡峭程度。设模型最后一层输出的未归一化对数得分为 logits 向量 z = (z1, z2, …, z|V|)，引入温度 T > 0 后的概率计算公式为：

Pi = \frac{exp(zi / T)}{∑j exp(zj / T)} ∝ pi1/T

（注：部分简化的示意图会将其口头表述为“将概率除以 T 再归一化”，但从代数上看，对已经算出的概率 pi 直接除以常数 T 再除以总和，常数 T 会在分子分母中直接约掉，分布不会发生任何改变；真正的温度缩放必须作用于 logits 除以 T 再取指数，等价于对原概率取 $1/T$ 次幂后再归一化。）

  • 当 T → 0 时，最高得分项的优势被无限放大，分布趋近于单点脉冲（One-hot），退化为确定性的贪心解码，适合数学推导、代码生成与结构化工具调用。
  • 当 T > 1 时，各项差异被拉平，低概率词元获得更多采样机会，适合需要发散创意的开放式写作或多样化路径探索。

Beam search 与任务权衡

如果希望寻找整体序列概率更高的完整输出，可以使用束搜索（Beam Search）：在每个时间步同时维护 B 条（Beam Width）累计对数概率最高的候选前缀路径，每步扩展后再剪枝保留前 B 条。Beam Search 常见于机器翻译等强约束生成任务，但它需要消耗 B 倍的显存与计算开销；而在 Agent 场景中，序列的语言模型概率最高并不等价于工具调用语义正确或任务成功，因此现代 Agent 更常采用低温单路解码，或结合外部验证器（Verifier）进行多路高温采样。

架构演变

回顾序列建模架构的演进史，每一次架构跃迁都在解决前一代模型的记忆与计算瓶颈：

  1. N-gram 语言模型（2010 年以前）：基于马尔可夫假设，只统计前 N-1 个词的共现频次，无法捕捉长距离依赖，也无法泛化未见过的词组组合。
  2. 前馈神经语言模型（Bengio et al., 2003）：引入分布式词向量表示（Word Embeddings），使语义相近的词在向量空间中彼此靠近。
  3. 循环神经网络与长短期记忆网络（RNN, 2010 / LSTM, 1997 提出、2014 普及）：通过隐藏状态 ht = f(ht-1, xt) 逐步传递任意长度的历史信息，但由于时间步之间存在严格的串行依赖，既无法在训练时充分利用 GPU 并行计算，又容易在长序列上出现梯度消失或信息遗忘。
  4. Transformer（Vaswani et al., 2017）：彻底抛弃循环结构，完全依靠注意力机制（Attention）让序列中任意两个位置直接建立联系，奠定了现代大语言模型的计算基石。

2. Transformer 的内部数据流

Encoder–decoder 与 decoder-only

2017 年原始的《Attention Is All You Need》论文针对机器翻译设计了编码器—解码器（Encoder-Decoder）架构：编码器双向读取源语言句子，解码器自回归生成目标语言。而今天几乎所有主流生成式大语言模型（如 GPT 系列、Claude、LLaMA、Qwen）都采用精简的 Decoder-only（纯解码器） 架构：输入提示（Prompt）与模型生成的回答处于同一个自回归序列中。

当一段文本进入 Decoder-only Transformer 时：

  1. 首先通过分词器切分为 Token ID，并经由词嵌入矩阵（Embedding Layer）映射为稠密向量；
  2. 加上位置编码（Positional Embedding，如 RoPE 旋转位置编码）以注入词序信息；
  3. 依次穿过 L 层相同的 Transformer Block；
  4. 最后经由线性投影层（LM Head）映射回词表维度，通过 Softmax 得到下一个 Token 的概率分布。

Q、K、V 与 scaled dot-product attention

在每一个 Transformer 层内部，输入向量首先经过层归一化（Pre-LayerNorm）以稳定数值分布，随后通过三个独立的线性变换矩阵 WQ, WK, WV 投影出三个核心表征：

  • 查询向量（Query, Q）：代表当前位置正在寻找什么信息；
  • 键向量（Key, K）：代表每个历史位置包含什么特征标签；
  • 值向量（Value, V）：代表每个位置被命中后实际提供的信息内容。

缩放点积注意力（Scaled Dot-Product Attention）的计算过程如下：

Attention(Q, K, V) = softmax(QK^⊤ + M√dk) V

其中 QK^⊤ 计算所有位置两两之间的匹配得分；除以缩放因子 √dk（Key 向量的维度平方根）是为了防止维度较高时点积方差过大，导致 Softmax 进入梯度极小的饱和区；最后用归一化后的注意力权重对 V 进行加权求和，再乘上输出投影矩阵 WO 映射回模型隐藏层维度。

Causal mask

为什么在训练 Decoder-only 模型时，我们可以把整篇文档成千上万个 Token 一次性并行输入给 GPU，而模型却不会“作弊”偷看后面的标准答案？秘密就在于公式中的因果掩码（Causal Attention Mask, M）。

M 是一个上三角部分全为 -∞、主对角线及下三角全为 $0$ 的矩阵。在计算第 t 个位置的注意力得分时，所有位于 t 之后的未来位置（j > t）的得分都会被加上 -∞，经过 Softmax 后权重严格变为 $0$。这样既保证了每个位置只能利用过去的信息，又让整段序列的所有位置能够在训练阶段通过单次矩阵乘法并行算出损失。

多头、残差、归一化和前馈层

单一注意力分布往往只能聚焦于某一种语义或语法关联。多头注意力（Multi-Head Attention）使用多组独立的投影矩阵 (WQ(h), WK(h), WV(h))，让模型在多个不同的表示子空间中并行关注不同维度的上下文关系（如有的头关注指代消解，有的头关注函数括号配对），随后将所有头的输出拼接（Concatenate）起来，通过一个更大的输出矩阵 WO 融合。

注意力子层的输出会通过残差连接（Residual Connection）直接与该层的原始输入相加（x + SubLayer(LN(x))），为梯度反向传播提供直通高速公路；接着再经过一次 LayerNorm 与逐位置的前馈神经网络（Feed-Forward Network, FFN / MLP）进行非线性特征变换。多层堆叠正是通过不断重复“全局注意力信息路由 + 局部 MLP 特征变换”来实现深度推理的。

并行性与二次复杂度

虽然 Transformer 解决了 RNN 无法并行训练的痛点，但它付出了另一个沉重代价：标准自注意力对序列长度 n 具有 O(n2) 的计算与显存复杂度。因为每个 Token 都要与前面所有 Token 计算点积，当上下文窗口从 4K 增长到 128K（扩大 32 倍）时，n × n 的注意力矩阵开销会暴增 1,024 倍。这就是长上下文 Agent 面临的底层算力墙。

3. 线性、混合注意力与上下文

Linear attention 的直觉

如何打破 O(n2) 的二次方魔咒？线性注意力（Linear Attention，Katharopoulos et al., 2020） 给出了一个极其优美的代数洞察。

在标准注意力 softmax(QK^⊤)V 中，我们之所以必须先算出形状为 n × n 的巨大矩阵 QK^⊤，是因为外层套了一个非线性的 softmax(·) 函数。如果我们暂时去掉 Softmax（或者用核特征映射 φ(Q)φ(K)^⊤ 替代），根据矩阵乘法结合律：

(QK^⊤)V = Q(K^⊤ V)

运算顺序一旦改变，奇迹就发生了：K^⊤ ∈ ℝd × n 与 V ∈ ℝn × d 相乘，得到的是一个形状仅为 d × d 的紧凑矩阵！无论序列长度 n 是 1 万还是 100 万，特征维度 d 是固定的常数，整体计算复杂度瞬间从 O(n2 d) 降到了对序列长度呈线性的 O(n d2)。

更进一步，在自回归逐步生成时，前缀的累积矩阵 St = ∑i=1t ki^⊤ vi 可以写成递归形式：

St = St-1 + kt^⊤ vt,   ot = qt St

这揭示了一个深刻的统一性：线性注意力下的 Transformer 本质上就是一个具有矩阵隐藏状态 St 的循环神经网络（“Transformers are RNNs”）。它既可以在训练时按块并行计算，又可以在推理时只维护固定大小的递归状态 St，无需保存随长度无限膨胀的 KV Cache。

线性化的边界

天下没有免费的午餐。固定维度的状态矩阵 St ∈ ℝd × d 本质上是对全部历史信息进行有损压缩。当序列非常长时，大量历史键值被叠加进同一个固定大小的矩阵中，模型在执行“精确大海捞针”（例如从十万字日志里原封不动找出一串特定的 32 位哈希值或早期的精确数字）时，召回能力往往明显弱于保留了每一个历史 Token 独立向量的标准全注意力（Full Attention）。此外，实际的线性注意力算法（如 RetNet、Mamba、Gated DeltaNet 等）通常还需要引入核特征映射、归一化分母或门控遗忘机制来维持数值稳定与表达力。

Full、linear、hybrid 的比较

为了兼顾长序列效率与精确检索能力，现代前沿模型（例如课件展示的 Kimi 线性/混合架构等探索）越来越多地采用混合注意力架构（Hybrid Attention）：

注意力架构每步推理存储状态序列长度复杂度核心优势典型短板
Full Attention（标准全注意力）随长度 n 线性增长的 KV CacheO(n2)任意距离精确召回（Exact Recall）与细粒度关联最强超长上下文下显存占用与解码延迟高昂
Linear Attention / SSM（线性注意力）固定大小的状态矩阵 StO(n)推理显存恒定，超长序列吞吐量极高固定状态容量有损压缩，精确字面回溯较弱
Hybrid Attention（混合注意力）少量全注意力层 KV + 大量线性层状态介于两者之间每隔若干层线性注意力穿插一层全注意力（如 3:1 或 7:1），兼顾长程吞吐与精确检索架构与推理引擎调度更为复杂

上下文长度的多个限制

作为 Agent 构建者，看到模型宣传支持“1M 上下文窗口”时，需要清醒地区分四个不同层面的长度限制：

  1. 位置编码上限：模型在数学结构上能否表示这么远的位置索引；
  2. 训练序列分布：模型在预训练和后训练阶段是否真正见过如此长的高质量连贯序列；
  3. 硬件显存上限：当前 GPU 显存能否装下对应长度的 KV Cache；
  4. 有效利用长度（Effective Context Length）：模型在长上下文中是否真的能准确提取并综合推理中间部分的信息，而不发生性能塌陷。

模型与 harness 匹配

不同的底层架构与训练配比，使得不同模型在“长文档单次读取”与“多步短上下文工具调用”上的表现截然不同。有的模型适合把大批材料直接塞进上下文，有的模型则更适合通过精简的运行底座（Harness）按需调用搜索工具分段读取。构建系统时，必须让 Harness 的上下文管理策略与所选模型的注意力特性相匹配。

4. 从预训练到对齐与 Agent 训练

交叉熵目标

大语言模型的能力从何而来？第一阶段是大规模预训练（Pretraining）。模型在数万亿 Token 的海量文本上做一件看似简单的事：给定前文，预测下一个真实 Token，并通过最小化交叉熵损失（Cross-Entropy Loss，即正确下一词元的负对数概率 -log P(xt \mid x<t)）来更新参数。

例如，在前面的例子中，若真实下一词是 "how"，而模型给 "how" 预测的概率为 P(how) = 0.0124，那么这一步的负对数损失在以 $10$ 为底时为 -log10(0.0124) ≈ 1.907，在深度学习标准的自然对数下则为 -ln(0.0124) ≈ 4.390（对比不同论文报告的 Loss 或困惑度 Perplexity 时，务必留意对数底数与分词器粒度是否一致）。

预训练数据清洗

预训练模型的上限取决于数据质量。从原始互联网抓取（如 CommonCrawl）到可训练语料，需要经历严密的清洗流水线：网页正文提取（HTML 解析与去噪）→ 语言识别与过滤 → 启发式规则与模型质量打分过滤 → 模糊去重（Deduplication）。像 The Pile、DCLM 以及针对数学推理专门清洗的 Nemotron-CC-Math 都证明了：精心过滤的高质量数据集，能够让同尺寸模型获得远超粗糙海量数据的推理底座。

数据配比与 mid-training

在通用预训练与最终微调之间，现代大模型普遍引入了中期训练（Mid-training）阶段，并高度重视数据配比（Data Mixing，如 Olmix 等研究）。为什么不能直接拿通用预训练模型去做少量的末端指令微调？《The Fine-Tuning Fallacy》与《Midtraining Bridges Pretraining and Posttraining》等研究指出：如果模型在预训练阶段没有充分吸收代码、长链条数学推导、结构化轨迹与长上下文语料，仅靠后训练阶段几万条样本的微调，只能教会模型“模仿回答的语气和格式”，却无法凭空注入深层的领域推理能力。Mid-training 正是通过提高高质量代码、数学、合成推理轨迹与长文本的混合比例，为后续的 Agent 能力打下坚实基础。

Instruction tuning / SFT

预训练模型只会“顺着往下续写文本”（比如你输入“帮我查一下明天的天气”，它可能续写出“，再帮我订一张机票”）。为了让模型听懂指令并扮演助手角色，需要进入监督微调（Supervised Fine-Tuning, SFT / Instruction Tuning）：在成千上万条高质量的（指令，期望回复）或（用户请求，思考过程，工具调用，环境观察，最终回答）多轮示范轨迹上继续使用交叉熵损失训练，使模型学会对话格式与工具使用规范。

RLHF 与偏好数据

SFT 让模型学会了模仿示范，但很多时候“评判两个回答哪个更好”比“亲手写出完美示范”容易得多。基于人类反馈的强化学习（RLHF） 或直接偏好优化（DPO）通过收集人类（或强模型）对成对输出 (ywin, ylose) 的偏好比较数据，训练奖励模型并引导生成策略对齐人类偏好。但人类偏好数据也存在固有盲区：标注者往往偏爱长篇大论、排版华丽、语气自信或顺从用户错误前提（Sycophancy）的回答，这反而可能诱发模型“不懂装懂”。

RLVR 与可验证奖励

对于代码编写、数学证明与 Agent 任务执行，我们拥有比主观偏好强大得多的信号——基于可验证奖励的强化学习（Reinforcement Learning with Verifiable Rewards, RLVR）。

  • 在数学题中，最终数值答案是否匹配标准答案是可精确验证的；
  • 在形式化定理证明（如 Lean）中，编译器能否通过证明检查是百分之百确定的；
  • 在软件工程 Agent（如 SWE-smith 生成的仓库修复任务）中，修改后的代码能否跑通单元测试套件（Unit Tests）是客观可判定的。

RLVR 让模型在真实或合成环境中自主探索多步推理与工具调用轨迹，只要最终结果通过验证器即给予正奖励，从而涌现出自我纠错、回溯与长链推理能力。不过需要注意，只要有自动化评分器，模型就有可能寻找评分逻辑的漏洞（Reward Hacking），因此验证器本身的严密性至关重要。

5. 推理系统与测试时扩展

GPU roofline 与瓶颈

当我们将训练好的模型部署为 Agent 的大脑时，推理性能受制于 GPU 硬件的两个物理上限（即 Roofline 模型）：计算吞吐上限（FLOP/s，算力瓶颈 Compute-bound） 与 显存带宽上限（Bytes/s，访存瓶颈 Memory-bandwidth-bound）。

大模型的一次生成请求天然分为两个截然不同的阶段：

  1. 预填充阶段（Prefill Phase）：一次性并行处理用户输入的所有 Prompt Token（包括系统提示、工具定义、长文档与历史记录）。此时矩阵乘法规模大、算术强度高，主要受限于 GPU 计算吞吐（Compute-bound），决定了首字延迟（Time to First Token, TTFT）。
  2. 解码阶段（Decode Phase）：每次只自回归生成 1 个新 Token。每生成 1 个词，GPU 都必须把几百亿参数的模型权重和全部历史 KV Cache 从高带宽显存（HBM）搬运到计算单元一次。此时计算量极小而搬运量极大，严重受限于 显存带宽（Memory-bound），决定了每个输出 Token 的生成耗时（Time per Output Token, TPOT）。

在 Agent 循环中，往往是“输入上下文极长（数万 Token 的历史与工具观测），单步输出较短（几十 Token 的工具调用指令）”，理解 Prefill 与 Decode 的物理差异是优化 Agent 延迟与成本的前提。

KV cache

在自回归解码第 t 个 Token 时，为了计算注意力，我们需要前面第 $1$ 到 t-1 个位置的所有 Key 和 Value 向量。如果每生成一个新词都把前面所有词重新算一遍 K 和 V，计算量将是灾难性的。因此，现代推理引擎都会将已计算过的前缀 Token 的 Key 和 Value 缓存在显存中，这就是 KV Cache。

KV Cache 避免了重复计算，但它的体积随层数、注意力头数、隐藏维度和序列长度线性增长，成为长上下文推理中消耗显存的头号大户。更重要的是，在跨轮次的 Agent 调用中，只要两次调用的消息前缀（Prefix）完全一致，推理服务端就可以通过 Prompt Caching（前缀 KV 缓存复用） 直接跳过前序 Token 的 Prefill 计算，将首字延迟与输入 Token 费用降低多达 50%–90%。

性能指标

在评测与监控 Agent 推理系统时，切忌只看一个笼统的“平均响应时间”，而应当拆解记录三项核心指标：

  • TTFT（Time to First Token）：从发出请求到收到第一个输出 Token 的时间，反映长提示词的处理与前缀缓存命中情况；
  • TPOT（Time per Output Token）/ 吞吐率（Tokens/sec）：解码阶段每秒生成的 Token 数量；
  • 端到端延迟（End-to-End Latency）：等于 TTFT + TPOT × 输出 Token 数。

Speculative decoding

既然 Decode 阶段的瓶颈在于每次搬运大模型权重只产出 1 个 Token（显存带宽利用率高但算力闲置），能不能一次搬运权重验证多个 Token？投机解码（Speculative Decoding） 正是利用了这一硬件特性：

  1. 先用一个参数量极小、速度飞快的草稿模型（Draft Model）连续快速猜出接下来 k 个候选 Token（例如猜出 {"path": "test.py"}）；
  2. 然后将这 k 个草稿 Token 一次性送入庞大的目标模型（Target Model），利用单次并行前向传播同时算出这 k 个位置的真实概率分布并逐一验证；
  3. 凡是通过验证的前缀全部一次性接受，遇到第一个不一致的位置则按修正后的分布重采样并继续。

投机解码在数学上保证了最终输出的概率分布与目标模型逐字解码完全一致（无损加速）。在代码生成、JSON 工具调用等格式高度可预测的 Agent 场景中，草稿命中率极高，能够带来显著的延迟降低。

推理长度与 reasoning budget

进入推理模型（Reasoning Models）时代，我们不仅可以靠扩大模型参数规模（Pretraining Scaling）提升效果，还可以通过在测试时让模型生成更长的内部思考链来提升准确率，即 测试时计算扩展（Test-time Scaling）。

例如计算一道容易掉入直觉陷阱的题目：“一件 80 美元的商品先涨价 25%，再降价 25%，最终价格是多少？”直觉抢答容易脱口而出“80 美元”，而展开中间步骤：80 × 1.25 = 100，100 × (1 - 0.25) = 75 美元，就能稳稳得出正确答案。

但更长的推理链也意味着更高的延迟与 Token 账单，且简单问题过度思考反而浪费资源。因此，现代模型与工程体系引入了显式的推理预算控制（Reasoning Budget）：例如 GPT-OSS 等模型提供的不同推理强度档位（low / medium / high reasoning effort）、在强化学习目标中加入长度惩罚（如 Inkling 的预算控制训练），以及通过多教师蒸馏（如 Kimi 的长度感知训练）让模型学会“简单问题简短答，复杂问题深入想”。

多次采样与 verifier

Test-time Scaling 的另一个维度是并行多次采样（Repeated Sampling / Best-of-N）：对同一任务采样 N 条候选轨迹，再从中选出最优解。

  • 当存在可靠的外部验证器（Verifier，如代码编译器、单元测试或形式化检查器）时，随着采样次数 N 增加，至少命中一次正确解的概率（pass@k）会大幅攀升；
  • 当缺乏外部验证器时，只能退而求其次采用多数投票（Majority Voting / Self-Consistency）或奖励模型打分（Reward Model Reranking），此时性能很快会在模型自身的认知盲区处饱和。

在工程对比中，比较不同方案时必须固定总计算预算（Total Token Budget 或总耗时），公平权衡“用小模型采样 10 次 + 验证器”与“用超大模型单次推理”的性价比。

6. 结构化输入输出

结构作为共享契约

在普通聊天场景中，模型输出一段自然语言就足够了；但在 Agent 系统中，模型的输出往往要直接作为下游 Python 函数、数据库查询或外部 API 的输入。此时，结构化格式（如 JSON Schema）就是语言模型与宿主程序之间的共享契约（Shared Contract）。需要注意的是，模型输出一段“看起来像 JSON 的文本”并不等于它能通过 Schema 校验；而通过了语法与类型校验，也不代表其中的业务语义（如日期是否合理、权限是否合规）一定正确。

Constrained decoding 与 FSM

如何从根本上杜绝模型输出缺引号、少括号或捏造非法字段名的格式错误？受限解码（Constrained Decoding，如 SGLang、Outlines 等推理引擎采用的技术） 将目标 JSON Schema 或正则表达式编译为一个有限状态机（Finite State Machine, FSM）。

在解码的每一个时间步：

  1. 状态机根据目前已生成的字符串前缀，确定当前所处的语法状态（例如当前正在生成布尔字段 "urgent": 的值）；
  2. 推理引擎直接在词表 logits 上生成掩码，将所有不符合当前语法状态转移的 Token 概率强制设为 -∞（例如只允许生成 "true" 或 "false" 对应的 Token）；
  3. 甚至当后续一段字符完全确定（如固定键名 ","reason":"）时，状态机可以直接一次性跳跃填充（Jump-forward decoding），无需逐 Token 调用大模型计算，既保证了 100% 的语法合法性，又加快了结构化生成速度。

Signatures、分类头与 tool calling

在工程框架层面，结构化输入输出有三种常见实现形态：

  • 声明式签名（如 DSPy Signatures）：用强类型类定义输入输出契约（例如声明 name: str、email: Optional[str]、intent: Literal["booking", "cancel", "inquiry"]），将任务契约与底层提示词解耦。
  • 专用分类头（Classification Heads）：对于高频、极低延迟的路由或安全判别任务（如 System One 类设计），直接在小模型顶部接分类头输出枚举类别概率，避免自回归生成冗余文本。
  • 原生函数调用（Function Calling）：将工具名称、描述与参数 JSON Schema 注册到模型上下文中，让模型在“直接回复用户”与“生成结构化工具调用”之间自主抉择。

7. Context engineering

上下文的组成

如果把大语言模型的上下文窗口比作计算机的内存（RAM），那么 上下文工程（Context Engineering） 就是研究如何高效分配和管理这块珍贵的内存空间。在 Agent 运行时，上下文窗口通常由五部分共同争夺空间：

  1. 系统指令（System Instructions）：角色设定、全局规则与行为边界；
  2. 工具定义（Tool Definitions）：所有可用函数的名称、说明与参数 Schema；
  3. 跨会话记忆与知识库检索片段（Memory & Retrieved Docs）；
  4. 对话与动作历史（Conversation & Action History）；
  5. 工具返回的观测输出（Tool Observations，如文件内容、终端日志）。

上下文工程的第一原则是：绝不要因为窗口还塞得下，就把所有东西一股脑全倒进去。每一段进入上下文的信息都应当有明确的用途与生命周期。

Context rot 与 OOLONG

随着上下文中堆积的历史记录和无关工具输出越来越长，即使远未达到模型的物理窗口上限，模型的推理准确率和指令遵循能力也会出现明显退化，这一现象被称为上下文腐化（Context Rot）。诸如 OOLONG 等长上下文推理与聚合评测基准表明，当关键信息被淹没在数万 Token 的冗长历史中时，模型不仅检索召回率下降，跨段落计数、比较与多步逻辑聚合的错误率更会急剧上升。

精简工具和按需读取

为了对抗 Context Rot，优秀的 Agent 设计遵循最小化与按需加载（Just-in-time Loading）原则：

  • 精简核心工具集：例如极简编码底座 Pi 仅暴露 4 个正交的基础工具（read、write、edit、bash），系统提示不到 1,000 Token。相比一次性往上下文里塞入上百个冗长重叠的专用 API 定义，精简的工具集能显著降低模型选错工具的概率，并留出充裕的窗口空间处理真实任务证据。
  • 渐进式读取：不预先把整个文档库或全部记忆拼进系统提示，而是先提供精简的目录或摘要，让 Agent 通过 search_docs、read_doc 或 recall 工具在需要时按需分页读取。

前缀稳定与缓存

在多轮 Agent 循环中，设计上下文布局还必须考虑 KV Cache 的前缀稳定性。如果我们在每一轮调用时都动态修改系统提示词开头的文字（比如在系统提示开头放一个每秒变化的当前时间戳，或者每轮重新洗牌工具列表的顺序），就会导致整个前缀的 KV Cache 全部失效，每一轮都不得不重新对数万 Token 的历史做全量 Prefill。

正确的工程做法是：保持 [System Prompt + Tool Schemas + 早期历史] 严格稳定不变，将新增的用户消息、动作与工具观测严格以追加（Append-only）方式放在序列末尾，只有在触发上下文压缩阈值时才进行阶段性重组。

Compaction

当长程任务的累计 Token 数逼近上下文预算上限时，必须启动上下文压缩（Compaction）：调用辅助模型（或压缩模块）将较早的多轮“思考—行动—巨型观测”历史浓缩为结构化的进度摘要。一份合格的压缩摘要必须完整保留：用户的原始目标与硬性约束、目前已确认的关键事实与参数（如查到的报销限额、文件路径）、已完成的动作，以及尚未解决的待办事项，同时丢弃已被消费掉的冗长中间日志。

Recursive Language Models

面对远超单次上下文窗口的超大规模信息处理任务（例如分析成百上千封邮件或大型代码库），除了被动压缩，还可以采用递归语言模型（Recursive Language Models, RLM）的思路：将超长上下文视为一个外部可编程环境，主模型不直接硬读全文，而是通过编写循环脚本或递归派发子模型调用（Sub-calls）分片检查数据、汇总中间变量，最后整合得出全局结论。

动手练习

  1. 温度缩放与解码计算：假设某一步词表仅含三个候选 Token，模型输出的原始概率分布为 p = [0.6, 0.3, 0.1]（对应对数 logits z = ln p）。请分别手算在温度 T = 0.5 和 T = 2.0 下经过 softmax(z / T) 归一化后的新概率分布，并验证为什么“直接将概率 pi 除以 T 再归一化”无法改变分布。
  2. KV Cache 与复杂度估算：画出一个标准 Decoder-only Transformer 层的完整数据流图（标出 LayerNorm、WQ/WK/WV、Causal Mask、Softmax、WO、残差连接与 FFN）。假设模型有 32 层、隐藏维度 d = 4096、采用 FP16（每浮点数 2 字节），请计算当上下文长度从 4,096 增长到 65,536 时，单条请求的 KV Cache 显存占用从多少 MB 增长到了多少 GB。
  3. 前缀缓存与上下文压缩实验：针对一个需要连续调用 15 次工具的多步查询任务，设计一套追加式消息布局与触发式压缩（Compaction）策略。明确写出：（a）哪些部分在每轮调用间保持字节级不变以命中 Prompt Cache；（b）当 Token 计数达到预算上限时，压缩提示词应要求辅助模型保留哪四类核心信息。
