第 13 讲｜评测基础与基准设计

在单轮分类或抽取任务中，评测往往只需要一行代码：accuracy = mean(y_pred == y_true)。然而，当我们评测一个在开放环境中多步运行的 AI Agent 时，情况变得空前复杂：同一个请求，Agent A 可能用 3 步 grep 就干净利落地找到了答案，Agent B 可能写了 15 步脚本把工作目录改得面目全非后也得出了相同答案，而 Agent C 在第一次运行时成功、第二次运行时却因为外部 API 延迟高了半秒钟而超时失败。

如果评测体系设计不当，我们很容易把“环境残留的脏数据”当成模型实力，把“更宽松的 Token 预算或更强的外部脚手架”误认为底层模型的进步，或者被几个跑通的幸运样本掩盖了系统在生产环境中的脆弱性。本讲将系统建立 Agent 评测基础与基准设计（Evaluation Fundamentals & Benchmark Design） 的方法论：剖析为什么 Agent 评测如此困难，掌握将任何 Agent 评测任务形式化为 四元组框架（Request、Environment、Stopping Criteria、Scorer） 的设计规范，并深入探讨优秀基准的黄金属性、真实脚手架（Realistic Scaffolding）的控制变量法则以及多维度的可靠性评估体系。

学习目标

  • 深入理解评测自主 Agent 相较于静态模型评测的四大核心难点（路径非唯一性、有状态环境变更、随机波动与多维成本安全约束）。
  • 熟练掌握 Agent 评测的四元组框架（The 4-Tuple Framework：Request、Environment、Stopping Criteria、Scorer），能够独立设计严谨无漏洞的四个组件。
  • 掌握优秀评测基准（Good Benchmarks）的设计原则（代表性、规格与评分对齐、抗饱和、防泄漏与可复现）以及真实脚手架（Realistic Scaffolding）的公平比较条件。
  • 建立超越单一“平均通过率”的多维可靠性视角：掌握跨运行一致性、抗扰动鲁棒性、故障恢复与可预测终止的量化评估方法。

知识讲解

1. Agent 评测为什么难

多步与状态变化

为什么评测一个 Agent 比评测一个静态语言模型困难得多？根源在于 Agent 运行的四个本质特征：

  1. 求解路径的多样性与非唯一性（Open-ended Trajectories）：完成同一个目标往往有无数条合法的工具调用路径。如果评分器死板地检查“第 1 步是否调用了函数 X”，就会把采用更聪明解法的 Agent 误判为失败；反之，如果只看最终输出的一句文字，又可能漏掉中间过程发生的严重违规。
  2. 有状态的环境变更与副作用（Stateful Environment & Side Effects）：Agent 的动作会真实修改文件系统、数据库或外部服务状态。如果两次测试之间没有彻底重置环境，前一次运行留下的文件或缓存会直接污染后一次运行；而且有些错误动作（如误删正常文件、向错误收件人发信）即使事后输出了正确文字也已造成不可逆损害。
  3. 多层叠加的非确定性（Compounded Non-determinism）：模型采样本身的随机性，加上外部工具响应时间、网络状态与并发调度的微小波动，会在长达十几步的循环中被逐级放大，使得单次运行（Single Trial）的结果具有极大偶然性。
  4. 成功的多维性（Multi-dimensional Success）：在实际工程中，“答对问题”只是底线；花掉 0.02 美元耗时 3 秒完成，与花掉 5 美元耗时 10 分钟、触发三次权限警告才完成，在工程价值上天差地别。

2. 四元组的逐项设计

为了将千变万化的 Agent 任务纳入严谨、统一的工程规范，本课程采用 四元组框架（The 4-Tuple Framework） 来形式化定义任何一个评测任务：

Evaluation Task = (Request, \ Environment, \ Stopping Criteria, \ Scorer)

设计一道评测题，本质上就是精确定义这四个组件及其交互边界。

Request

1. 请求（Request）：呈现给 Agent 的初始任务指令（以及在交互式评测中由模拟用户逐步提供的追问或澄清信息）。

  • 设计准则：必须区分“故意测试模糊需求澄清能力”与“出题人自己没把规格写清楚”。如果一道题目的意图是考核执行能力，那么所有会被后续 Scorer 检查的硬性要求（如输出文件路径、JSON 字段名、日期时区口径、格式限制）都必须在 Request 中明确给出；如果一道题专门用于测试 Agent 在信息不足时能否主动调用 ask_user 提问（如 HW1 中的澄清 Persona），则应当将缺失的关键背景信息明确写入模拟用户的隐藏知识库（Hidden Knowledge）中，待 Agent 提问时按规则披露。

Environment

2. 环境（Environment）：Agent 在执行任务期间所感知和操作的外部世界，包括初始文件系统、数据库记录、可用的工具集（Tools & Schemas）、沙箱权限配置以及模拟用户角色。

  • 设计准则：环境设计的核心铁律是确定性初始化与严格隔离重置（Deterministic Reset & Isolation）。每一次 Trial 启动前，评测框架都必须从只读镜像或干净快照创建全新的临时工作目录（Workspace）与全新的记忆目录（除非专门测试跨会话记忆延续），确保上一次 Trial 写入的任何字节都绝对无法泄漏到下一次 Trial 中。同时，环境中不应遗留包含标准答案的测试源码或Git提交历史，防止 Agent 走捷径偷看答案。

Stopping criteria

3. 终止条件（Stopping Criteria）：决定一次 Trial 何时结束并移交评分器的规则集合。

  • 设计准则：一个完备的评测运行底座必须同时定义主动终止与被动熔断两类条件：
    • 主动终止：Agent 正常返回最终自然语言回复（无后续工具调用），或显式调用了 finish / submit 工具；
    • 预算与边界熔断：达到最大允许交互轮数（如 max_turns = 15）、达到累计 Token 消耗或美元费用上限（budget_exceeded）、单次运行总墙钟时间超时（timeout_seconds）、或者连续 N 次输出无法解析的畸形工具调用（malformed_response）。
  • 所有的预算上限都是实验的自变量约束，在对比两个系统时必须严格锁死相同的 Stopping Criteria。

Scorer

4. 评分器（Scorer / Verifier / Grader）：在 Trial 终止后，接收最终环境状态、产出工件（Artifacts）与完整运行轨迹（Transcript），输出结构化得分与成败判定的函数。

  • 设计准则：优秀的 Scorer 遵循“结果状态优先，关键过程兜底”的混合校验原则：
    • 对最终环境状态的检查（Outcome State Verification）：例如检查数据库里的日程是否已按正确时间创建、生成的 /app/out.step 文件是否通过几何测试、工作区里是否生成了要求的目标文件；
    • 对过程证据与安全红线的检查（Trajectory & Safety Checks）：例如检查回答所引用的文档 ID 是否真的在运行轨迹中被 read_doc 读取过（防止瞎蒙正确数字却编造出处）、确认拒绝规则（deny_rules）拦截的危险命令执行次数严格为 $0$，并在评分输出中明确区分“答案错误”、“违反安全约束”、“预算耗尽”与“基础设施异常”。

3. 好基准与可靠性

Good benchmarks

当我们将几十或几百个四元组任务组合成一个基准测试套件（Benchmark）时，如何判断这是一个严谨的好基准（Zhu et al., 2025，《Establishing Best Practices for Building Rigorous Agentic Benchmarks》）？核心衡量标准包括五点：

  1. 生态效度与代表性（Ecological Validity）：任务来源于真实的应用痛点，而非脱离实际的文字游戏；
  2. 可解性验证（Verified Solvability）：每道题都配有经过实测的参考解（Oracle Solution），确保题目不是因环境缺失或自相矛盾而无解；
  3. 对多种合法路径的包容性（Path Agnosticism）：只要最终状态正确且未违反安全约束，无论是用 Python 脚本、Awk 命令还是分步工具调用完成，Scorer 都应一视同仁判过；
  4. 充足的难度梯度与抗饱和性（Headroom & Difficulty Spectrum）：既有检验基础功能的入门题，又有能够拉开顶尖模型差距的复杂长尾难题，避免基准发布即被刷到 99% 失去区分力；
  5. 防污染与版本透明（Contamination Resistance & Versioning）：提供清晰的训练/测试边界与语义化版本号。

Realistic scaffolding

在对比评测中，一个极易混淆实验结论的陷阱是脚手架偏差（Scaffolding Confounding）：

  • 当你的研究目标是比较不同底层模型（Model A vs. Model B）的能力时，必须固定相同的真实脚手架（Realistic Scaffolding）与预算，或者为每个模型配备其官方推荐的标准工具适配层，并完整披露提示词与重试逻辑；
  • 当你的研究目标是证明某项新架构或设计模式（如新增一个反思模块或上下文压缩算法）有效时，必须严格锁死同一个底层模型、同一套工具集和相同的总 Token / 时间预算上限，与未加该模块的强基线做消融对比（Ablation Study），防止把“多花了 3 倍 Token 预算”伪装成“算法架构优越”。

Reliability dimensions

最后，生产级评测绝不能只报告一个干巴巴的“平均准确率（Mean Pass Rate）”。一个严谨的评测报告应当从四个可靠性维度完整刻画系统表现：

  1. 多次运行一致性（Consistency：pass@1 vs. passk）：测量同一任务重复独立运行 k 次（通过设置不同的随机种子或缓存盐值 CS329Z_EVAL_SALT）时，连续 k 次全部成功的概率 passk；
  2. 对输入与环境扰动的鲁棒性（Robustness to Perturbations）：当用户换一种同义口吻提问、文档列表中多混入几篇无关干扰文档、或某个工具首次调用偶发返回超时错误时，系统成功率的变化幅度；
  3. 可预测与安全的失败行为（Graceful Degradation & Safety Compliance）：当任务确实超出能力范围或权限被用户拒绝时，Agent 能否诚实汇报原因并优雅降级，而不是强行编造事实（Fabrication）或绕过限制；
  4. 帕累托效率曲线（Cost-Latency-Accuracy Tradeoff）：同时记录并展示每个任务切片的成功率、平均耗时、平均模型调用轮数与实际美元成本。

原课程阅读清单与导读

  • Zhu et al. "Establishing Best Practices for Building Rigorous Agentic Benchmarks." (2025). 导读：系统梳理当前主流 Agent 基准在任务真实性、环境隔离、评分器漏洞与可复现性上的常见缺陷及改进规范 checklist。
  • 拓展阅读：Press. "How to Build Good Language Modeling Benchmarks." (2024). 导读：从基准构建者的实战视角理解如何提高信噪比、消除格式刷榜捷径并设计能够经受时间考验的测试集。
  • 拓展阅读：Polo et al. "tinyBenchmarks: Evaluating LLMs with Fewer Examples." ICML (2024). 导读：了解如何利用心理测量学中的项目反应理论（IRT）从大型基准中筛选出最具信息量的核心子集，用极少样本估算全局能力。

动手练习

  1. 编写完整的四元组评测规范：围绕办公助手的四个典型场景——（a）跨两封邮件核对项目定金金额、（b）新旧差旅餐费标准冲突判断、（c）用户拒绝执行脚本后改用只读命令完成统计、（d）需求指代不明需先向用户澄清——分别写出完整的四元组定义（Request、Environment、Stopping Criteria、Scorer）。
  2. 验证器正反例对冲测试（Positive & Negative Oracle Test）：针对上述 4 道四元组题目，为每道题手工构造一条“应当通过的参考轨迹（Positive Oracle）”与两条“看似合理但实则违规的欺骗轨迹（Negative Cases，如猜对金额但未读取对应邮件、或在被拒绝后仍残留了临时文件）”，编写 Python 评分函数并验证其能否 100% 准确区分正反例（直接衔接 HW2 评测实践）。
