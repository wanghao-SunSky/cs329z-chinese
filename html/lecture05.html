第 05 讲｜框架与持久编排

在早期深度学习时代，研究者需要用 NumPy 手动推导并编写每一层的反向传播梯度公式；直到 PyTorch 与 JAX 等框架出现，将自动微分、张量运算与硬件调度抽象为清晰的原语，才让构建复杂神经网络变得高效且不易出错。

AI Agent 的工程化正在经历完全相同的演进。在前四讲和 HW1 中，我们亲手用原生 Python 搭建了检索器、工具解析协议与 while 循环，目的是看清底层运行时的每一处细节；而在实际生产中，我们往往需要借助高层次的抽象框架来声明任务契约、编排复杂状态流、管理长周期持久执行并监控线上轨迹。本讲将围绕“从邮件提取日程并写入日历”这一统一的实战任务，深入对比 DSPy（声明式签名、模块与自动优化）、LangGraph（基于共享状态的有向图编排）、主流开源 Agent Harnesses（mini-SWE-agent、OpenHands、Pi、OpenClaw）的设计取舍，以及 Temporal（跨进程崩溃恢复的持久化执行引擎）与生产级可观测性体系。

学习目标

  • 从“数据（Data）、系统（System）、评测（Evals）”三大支柱理解框架抽象的价值，掌握从单模型调用、确定性工作流到自主 Agent 的控制权光谱。
  • 掌握 DSPy 的三大核心原语：Signatures（声明做什么）、Modules（定义如何组合） 与 Optimizers（利用数据与指标自动优化提示或权重）。
  • 掌握 LangGraph 的三大核心原语：State（共享状态工作区）、Nodes（读写状态的处理函数） 与 Edges / Conditional Edges（决定控制流转向的边）。
  • 对比剖析开源 Agent 底座（mini-SWE-agent、OpenHands、Pi、OpenClaw）在工具设计、历史管理与状态持久化上的架构权衡，理解 HarnessTax 与 Meta-Harness。
  • 理解 Temporal 的持久化执行模型（Client、Server、Workers、Workflows 与 Activities），掌握确定性重放（Replay）、活动重试策略、耐久计时器以及外部副作用的幂等边界。

知识讲解

1. 为什么需要抽象

从手写运算到系统抽象

框架存在的意义，是把重复、易错的样板代码（如提示词拼接、JSON 解析重试、状态传递、断点恢复与调用追踪）封装起来，让工程师能够专注于业务与研究的核心决策。在评估任何框架时，我们始终回到 AI 系统工程的三大支柱：

  1. 数据（Data）：训练样本、运行轨迹（Rollouts）、少样本示范与人类反馈；
  2. 系统（System / Model）：语言模型、复合工作流与 Agent 控制环路；
  3. 评测（Evaluation + Metric）：通过率、精确匹配、LLM 裁判得分以及成本与延迟指标。

优秀的抽象应当让这三根支柱的联动变得更清晰、更可组合，而不是把底层失败原因藏进黑盒里。

自主程度与可靠性

不同框架服务于“控制流光谱（Spectrum of Control Flow / Agency）”上的不同位置：

  • 模型 API 层（OpenAI / Anthropic API、vLLM、SGLang）：模型只是更大软件系统中的一个函数调用；
  • 工作流与复合系统层（DSPy、LangGraph）：系统的整体控制流与编排逻辑掌握在程序代码手中，模型在指定节点完成推理或路由判断；
  • 自主 Agent 底座层（OpenHands、Claude Code、Pi）：控制流交给 AI 模型自主决定，模型在多轮循环中动态选择工具并改变环境；
  • 基础设施横切层：像 Temporal 这样的持久化编排引擎负责跨进程容错与可靠性（Reliability），而 MLflow、LangSmith、Langfuse 等平台则负责全链路可观测性（Observability）。

2. DSPy：声明、组合、优化

Signature 声明要做什么

在传统提示工程中，开发者往往把“任务接口定义”、“输出格式约束”和“诱导模型思考的措辞技巧”全混在一大段冗长的字符串模板里。一旦更换底层模型或修改字段，就得重写整段字符串。

DSPy（Khattab et al., 2024） 将语言模型调用重构为声明式编程，其第一块基石是 Signature（签名）——它只严格声明输入是什么、输出是什么（What），而不硬编码具体提示词怎写：

PYTHON
import dspy
from typing import Literal, Optional

class ExtractEvent(dspy.Signature):
    """Extract calendar event information from an email."""
    email: str = dspy.InputField()
    event_name: Optional[str] = dspy.OutputField(desc="Name of the event, or None if no event")
    date: Optional[str] = dspy.OutputField(desc="Date in YYYY-MM-DD format")
    start_time: Optional[str] = dspy.OutputField(desc="Start time in HH:MM 24-hour format")
    duration_hours: Optional[float] = dspy.OutputField(desc="Duration in hours")

通过在 Signature 中使用 Python 类型注解（如 Literal["positive", "negative", "neutral"]、float、Optional[str]），DSPy 的适配器会自动在底层生成对应的格式化提示并解析校验模型输出，确保返回结果直接满足类型契约。

Module 定义怎么组合

声明了 Signature 之后，Module（模块） 决定了如何履行这一契约（How）。DSPy 提供了可自由替换与嵌套的内置模块：

  • dspy.Predict(Signature)：最基础的单次预测调用；
  • dspy.ChainOfThought(Signature)：自动在输出字段前注入一步 reasoning（思维链推导），让模型先思考再给出结构化字段；
  • dspy.BestOfN：多次采样并根据奖励函数挑选最优结果；
  • dspy.ReAct 与 dspy.RLM：将工具列表或长上下文环境接入模块，通过多步自主循环完成 Signature 所声明的目标。

正就像在 PyTorch 中编写 nn.Module 的 forward 函数一样，我们可以用标准的 Python 控制流将多个 DSPy 模块组合为复合程序。

Optimizer 使用数据与 metric

DSPy 最核心的突破在于第三块基石——Optimizer（优化器）。只要你准备好三样东西：

  1. 一个由 DSPy 模块组成的程序；
  2. 一批少量的训练/开发集样本（如几十封带标注的邮件）；
  3. 一个量化的评测指标函数 metric(example, prediction)；

DSPy 优化器（如 BootstrapFewShot、MIPROv2、GEPA）就能自动运行程序、收集成功轨迹作为少样本示范（Demonstrations），或自动演化各模块的系统指令（Instructions），从而在无需人工反复手改提示词的情况下最大化评测指标。

Notebook 的抽取与程序组合

在第 05 讲配套 Notebook（lecture5.ipynb）中，我们将两个 ChainOfThought 模块与本地日历客户端 tinycal 组合成一个完整的邮件日程更新程序：

PYTHON
class UpdateCalendarFromEmail(dspy.Module):
    def __init__(self):
        self.extract = dspy.ChainOfThought(ExtractEvent)
        self.pick_emoji = dspy.ChainOfThought("event_name -> emoji")

    def forward(self, email: str):
        extracted = self.extract(email=email)
        # 若邮件中不包含有效日程（缺少名称、日期或开始时间），直接跳过写入
        if not (extracted.event_name and extracted.date and extracted.start_time):
            return dspy.Prediction(added=False, event=None)
        emoji = self.pick_emoji(event_name=extracted.event_name).emoji
        # 调用外部日历服务写入事件
        event = cal.add(
            title=f"{emoji} {extracted.event_name}",
            date=extracted.date,
            start=extracted.start_time,
            duration=extracted.duration_hours or 1.0,
        )
        return dspy.Prediction(added=True, event=event)

这种写法将“自然语言理解（extract、pick_emoji）”与“确定性业务逻辑（if 非空校验与 cal.add 调用）”清晰地结合在了一起。

Notebook 的 GEPA 实验

在 Notebook 的优化实验中，我们将 50 封合成邮件按 seed=0 打乱，划分为 30 条训练集与 20 条测试集。最初使用轻量级模型运行未优化的抽取程序时，由于邮件中的相对日期推算（如“下周四”）和时长默认规则容易出错，测试集得分较低。

随后我们定义了评测指标 metric（精确核对日期 date、开始时间前 5 个字符 start[:5] 以及时长 duration），并调用 GEPA（Genetic Pareto Prompt Evolution） 优化器，设置最多约 100 次指标评估，利用更强的反思模型（Reflection LM）分析训练集上的错误轨迹并迭代改写 ExtractEvent 的指令说明。优化完成后，自动生成的指令详细补充了相对日期换算基准与缺省时长规则，使轻量级模型在独立测试集上的准确率大幅跃升。

工程审视：仔细观察该实验中的 metric 函数可以发现，它只校验了 date、start 和 duration，却没有校验 event_name 是否准确。这提醒我们：优化器只会忠实地迎合你编写的 metric；如果指标本身存在漏检维度，优化过程完全可能牺牲未受监控的字段质量。

Notebook 的 ReAct / RLM

当任务无法用固定的“先抽取、再添加”两步走完时（例如用户发来模糊指令：“帮我跟 Alex 约个明天下午有空的半小时喝咖啡，并把周五例会的图标改成火箭”），Notebook 进一步展示了两种动态模块：

  • dspy.ReAct：将 cal.today、cal.list、cal.find_free_slots、cal.add、cal.update 等工具交给模型，模型自主决定先查今天日期、再搜索空闲时段、最后执行创建或更新；
  • dspy.RLM（Recursive Language Model）：当需要一次性在整批 50 封邮件长列表中查找所有与特定地点（如 Gates 大楼）相关的活动时，dspy.RLM 通过在沙箱中编写并迭代执行代码（设置 max_iters=8）来遍历筛选数据，避免了单次长文本阅读的遗漏。

3. LangGraph：显式状态流

State、nodes、edges

如果说 DSPy 侧重于“声明式模块与自动编译优化”，那么 LangGraph 则侧重于将复合系统的控制流显式建模为一张操作共享状态的有向图（State Graph）。它由三个核心概念构成：

  1. 状态（State）：整张图的共享工作区（通常定义为 Python TypedDict 或 Pydantic 模型），保存跨步骤传递的所有字段（如原始邮件、抽取出的日程详情、选好的 Emoji、最终日历操作结果）。
  2. 节点（Nodes）：图中的计算单元。每个节点本质上是一个普通 Python 函数 node(state) -> partial_state，它从共享 State 中读取所需字段，调用大模型或外部工具，然后返回需要更新回 State 的字段字典。
  3. 边（Edges & Conditional Edges）：定义节点之间的控制流向。普通边表示固定顺序转移（如 START -> extract）；条件边（Conditional Edges） 则根据当前 State 中的内容动态决定下一步走向哪个节点（如 extract 之后根据字段是否齐全，分流至 pick_emoji 或直接跳至 END）。

抽取到日历的图

在日历任务中，使用 LangGraph 构建的工作流结构一目了然：

  • 定义 EventDetails（Pydantic 结构化输出模型）与 CalendarState；
  • 节点 extract_node 使用 llm.with_structured_output(EventDetails) 提取邮件信息；
  • 条件路由函数 route_after_extract(state) 检查 state["event"] 是否包含有效日程：若有效则走向 emoji_node -> add_calendar_node -> END；若邮件只是无关寒暄则直接走向 END。

这种显式状态图的优势在于控制流边界高度可视化、状态快照清晰，非常适合需要精确控制分支、循环、人工审批断点（Checkpointing）的复杂工程流程。

预构建 Agent 的真实入口

当我们需要在状态图中嵌入一个标准的 ReAct 工具调用循环时，既可以自己用两个节点（llm_node 与 tools_node）加一条判断是否有 tool_calls 的条件边手搭出来，也可以直接使用 LangChain / LangGraph 生态提供的预构建入口 from langchain.agents import create_agent（底层基于 LangGraph 运行时构建状态图），传入模型与日历工具函数列表即可快速启动交互式 Agent。

4. 开源 harness 的设计空间

Harness 包住模型做什么

走出工作流框架，当我们审视一个完整的自主 Agent 系统时，包裹在大语言模型外层的运行底座被称为 Agent Harness（智能体运行底座）。Harness 决定了四件核心设计：暴露哪些工具、如何组织记忆、如何管理上下文窗口、以及如何在执行环境中运行动作。

不同的开源 Harness 针对各自的目标场景做出了截然不同的架构取舍：

开源底座（Harness）工具集设计上下文与历史管理执行环境与容错特色适用定位与设计哲学
mini-SWE-agent极致精简：仅有 1 个 bash 工具完全线性的消息列表（每步直接 append）每次动作调用独立的 subprocess.run（无持久 Shell 状态）用不到百行代码证明极简底座即可跑通 SWE-bench
OpenHands丰富的开发工具（Bash、文件编辑、浏览器等）持久化事件流（Event Stream）：每步存为磁盘上的独立 JSON 事件文件，每轮调用前从事件流重建模型上下文维护持久化的 tmux 终端会话（保留 cd 目录与虚拟环境）；内置卡死检测器（连续 4 次重复相同动作与结果即自动终止）面向复杂长周期软件工程的工业级全功能平台
Pi Agent仅启用 4 个基础工具：read、write、edit、bash（系统提示 <1,000 Tokens）树形会话历史（Tree-structured History）：支持回退到任意早期消息节点并开辟新分支；支持技能文件与压缩直接以当前宿主进程权限运行，无内置审批、无子 Agent、无计划模式极致极简主义底座，通过插件扩展适应个人工作流
OpenClaw个人助手与多渠道通信工具将身份与长期记忆存储为本地 Markdown 文件（AGENTS.md、SOUL.md、USER.md、MEMORY.md）并注入系统提示单一长驻 Gateway 进程接管所有聊天渠道；每 30 分钟触发一次心跳轮次（Heartbeat）（无事时回复 NO_REPLY 保持静默），凌晨 3 点后台任务自动整理日记写入 MEMORY.md7×24 小时在线的主动式个人常驻 Agent

mini-SWE-agent

mini-SWE-agent 展示了“少即是多”的极端形态：它不定义任何专用文件读取或搜索工具，只给模型一个 bash 命令接口；每次执行都启动全新的子进程，不保留上一步的工作目录或环境变量；历史记录也只是最简单的线性追加。这种无状态设计极大简化了实现与并发测试，但也要求模型必须在单条命令中显式带上路径或环境激活前缀。

OpenHands

与极简路线相反，OpenHands 专为长周期复杂软件开发而设计。它把每一次用户输入、模型动作与环境输出都持久化为不可变的 JSON 事件日志（Event Log），每一轮模型调用所需的 messages 都是从事件日志动态投影重建的；同时它在后台维护一个持久化的 tmux 终端会话，使得 cd 切换目录、导出环境变量或激活 Python 虚拟环境能够自然延续到后续步骤，并通过循环检测器及时中断死循环。

Pi

Pi 则代表了面向开发者的可塑极简底座：默认只提供 read、write、edit、bash 四个原子工具，避免工具膨胀挤占上下文；最具特色的是它将对话历史保存为一棵树（Tree）而非单链表——当你在调试中发现 Agent 走入歧途时，可以直接回退到 5 步前的历史节点重新分支探索。不过由于 Pi 默认不设权限拦截与沙箱，在生产或不可信输入下必须额外包裹操作系统级隔离。

OpenClaw

OpenClaw 展示了常驻型主动式 Agent（Proactive Agent）的典型工程形态：通过每 30 分钟一次的定时心跳（Heartbeat）唤醒模型检查是否有待办事项（若无需打扰用户则输出 NO_REPLY），并通过凌晨后台任务（Sleep-time Compute）将白天的零散交互提炼归档到持久化的 MEMORY.md 中。

HarnessTax 与 meta-harness

为什么我们要花这么大精力研究 Harness？Arena.ai 的 HarnessTax 研究表明：同一个基础大模型，搭配不同的 Agent Harness 在编码基准上的得分差距甚至可以超过两代模型之间的差距；而且并没有哪套固定 Harness 对所有模型都最优——针对模型 A 精心调校的提示与工具格式，直接套在模型 B 上反而可能造成性能折损（即“底座税 Harness Tax”）。

更进一步，Meta-Harness（Lee et al., 2026） 提出不再靠人工凭经验手搓 Harness，而是引入一个元智能体（Meta-Agent），根据历史评测轨迹自动修改、搜索并演化 Harness 的代码结构与上下文策略，将底座设计本身纳入自动化优化闭环。

5. Temporal：持久执行

服务、工作流与活动

当一个 Agent 任务不再是 3 秒钟的问答，而是需要持续运行几十分钟甚至跨天（例如等待外部审批、定时跟进日程或执行多阶段长任务）时，普通的内存级 Python 脚本一旦遇到进程崩溃、网络抖动或机器重启，所有中间状态都会瞬间清零。

Temporal 是业界标准的持久化执行引擎（Durable Execution Engine）。它的核心架构将任务代码划分为两个职责截然不同的层次：

  1. 活动（Activities）：封装所有可能失败、耗时或具有非确定性副作用的外部操作（如调用大模型 API、请求第三方 REST 接口、读写外部数据库）。
  2. 工作流（Workflows）：纯粹用确定性代码编写的高层编排逻辑，负责按顺序、条件或定时器串联各个 Activities。

在运行时，你的客户端（Client）向 Temporal Server 提交工作流请求；Server 将任务放入持久化队列（Task Queue）并保存完整的执行历史与状态（Execution History & State）；外部的 Workers 进程从队列拉取 Workflow 与 Activity 任务并执行。

Replay 与确定性

Temporal 是如何做到“Worker 进程随时被强行杀死，重启后却能接着中断前的那一行代码继续往下跑”的？答案是基于事件历史的确定性重放（Deterministic Replay）。

每当一个 Activity（例如第一步 extract_event）执行成功，Worker 就会把它的输入和返回结果持久化记录到 Temporal Server 的事件历史（Event History）中。如果进程在第二步崩溃并重启，新的 Worker 会从头开始重新执行 Workflow 函数代码；但当执行到第一步 await workflow.execute_activity(extract_event, ...) 时，Temporal 发现事件历史里已经有了第一步的成功记录，便不会再去重新调用大模型，而是直接瞬间返回历史记录里的结果，一路快进恢复到崩溃前的精确位置！

正因为依赖重放机制，Workflow 编排函数内部必须严格保持确定性（Deterministic）——绝不能在 Workflow 函数里直接调用 random.random()、datetime.now()、直接发网络请求或直接调用 LLM，所有这些非确定性操作都必须放进 @activity.defn 中。

重试策略与超时

在配套 Notebook 中，我们将 extract_event、pick_emoji、add_calendar_event 封装为三个 Temporal Activities，并为工作流配置了重试策略（RetryPolicy：初始间隔 1 秒、最大重试 5 次、单次超时 1 分钟）。当我们在演示中故意植入一个前两次必定抛出 RuntimeError("Emoji service unavailable")、第三次才正常的故障版 pick_emoji 时，Temporal 自动捕获异常并仅对 pick_emoji 进行局部退避重试，而第一步已经完成的 extract_event 零重复开销，最终整个工作流平滑成功。

耐久计时器与 worker 重启

Notebook 最后演示了跨进程恢复的威力：启动一个子工作流，内部调用 await asyncio.sleep(20) 等待 20 秒后发送日程提醒。当计时进行到第 10 秒时，我们直接终止本地 Worker 进程；数秒后重新启动 Worker，工作流并没有从头再等 20 秒，也没有丢失任务，而是在剩余时间到期后准时完成了提醒——因为耐久计时器（Durable Timer）与事件状态都安全地保存在 Temporal Server 中。

副作用的边界

在使用 Temporal 等持久编排引擎时，必须清醒认识一条工程边界：Temporal 保证工作流状态与活动调度的持久恢复（At-least-once Activity Execution），但它不能替外部非事务接口变魔术般地消除副作用。如果 add_calendar_event 活动已经成功向外部日历写入了日程，但在把成功响应传回给 Worker 的半路上进程断网崩溃，Temporal 重试该 Activity 时就会再次调用写入接口，导致日历里出现两条重复日程。因此，凡是具有外部写副作用的 Activity，在生产环境中都应当设计业务幂等键（Idempotency Key）或在写入前先检查目标记录是否已存在。

6. 可观测性与框架选择

Trace 要记录什么

当线上 Agent 行为异常时，仅看最终输出的字符串是无法调试的。完整的全链路追踪（Tracing & Telemetry）应当以结构化跨度（Spans）记录每一次运行的全貌：每一步的模型输入提示词、生成的原始文本、解析出的工具调用与参数、工具执行的返回结果或异常栈、状态迁移、单步耗时、重试次数以及 Token 费用明细。

观测平台的角色

诸如 MLflow Tracing、LangSmith、Langfuse 等可观测性平台，能够将复杂的嵌套模块调用、LangGraph 节点跳转或 ReAct 循环可视化为直观的火焰图与调用树，并直接打通线上轨迹收集与离线评测集构建，支撑 “构建（Build）→ 运行（Run）→ 评测（Evaluate）→ 改进（Improve）” 的工程闭环。

评测应贴合实际领域

在选择框架与架构时，切勿盲目追求最复杂的自主 Agent 或照搬通用排行榜分数：

  • 如果任务逻辑固定、边界清晰，优先使用简单的确定性代码或轻量级工作流；
  • 如果需要优化多阶段提示词与结构化输出，DSPy 提供了极佳的声明式与自动优化范式；
  • 如果需要精细控制分支路由与状态持久化，LangGraph 与 Temporal 提供了坚实的工程底座；
  • 最重要的是，始终用贴合自己真实业务领域的代表性数据集与评测指标来检验每一次架构变更的真实收益。
