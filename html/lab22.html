学期项目指南｜设计、构建并严格评测 Agent 系统

贯穿全课程的学期项目（Course Project）是将你在课堂与作业中学到的模型、检索、工具、编排、记忆、多智能体、优化与安全技术融会贯通的核心舞台。你的目标是：围绕一个具有真实价值的开放问题，设计、构建并严格评测（Design, Build, and Rigorously Evaluate）一个智能体系统，或者构建一套深入揭示现有智能体失败模式的评测与优化体系。

1. 选题方向与核心工程原则

项目支持 1–3 人团队（或独立完成），选题应当紧密围绕本课程的三大支柱展开：

  1. 构建新型 Agent 系统（Building Agents）：结合检索（RAG）、工具调用、长程记忆、多 Agent 协作或上下文/权重优化，解决特定领域的复杂多步任务；
  2. 智能体数据工程（Data for Agents）：研究如何高效合成、筛选或从交互中采集高信息量的 Agent 训练与优化数据；
  3. 评测与安全防护（Evaluating & Securing Agents）：构建严谨的领域评测基准，系统揭示现有 Agent 在成本、延迟、长尾鲁棒性、隐私泄露或提示注入上的失效机理并提出改进方案。

极具参考价值的选题切入点包括：

  • 高价值垂直任务智能体：例如自动解析课程大纲并同步日历截止日的学术助手、跨代码库与文档的特定框架编程 Agent、研究文献自动发现与多跳对比综述系统；
  • 系统级权衡与鲁棒性研究：系统评估不同上下文管理策略（Observation Masking vs. Compaction vs. RLM）在超长任务上的成本—准确率帕累托前沿；研究 Agent 对工具偶发报错、API 变更或间接提示注入的防御恢复机制；
  • 深入的评测与诊断分析：针对某一类热门开源 Agent，构建细粒度的四元组基准，通过消融实验定位其“看似能跑通 Demo 但在真实分布下频繁失败”的核心瓶颈。

项目第一铁律：尽早定义评测（Define Evaluation Early）！ 在本课程中，“跑通了一次漂亮的现场演示（A demo that works once）”绝不构成充分的研究或工程证据。在立项的第一周，你就必须明确回答：你的测试任务集是什么？数据从哪里来？什么算成功？用什么代码评分器、LLM 裁判或人工指标来量化对比你的系统与强基线（Baselines）？

2. 论文格式与规范要求

项目的所有书面报告（Proposal、Midway Report、Final Report）均采用标准的 ICLR 会议论文 LaTeX 模板 排版（正文页数限制均不含参考文献 References 与附录 Appendices）：

  • 参考文献规范：所有引用文献按第一作者姓氏字母顺序排列，必须包含完整的作者列表、出版年份、完整标题与发表会议/期刊名称（参照 ICLR Author Guide）；
  • 安全与伦理考量（Safety & Ethical Considerations）：最终报告须专门讨论数据来源合规性、系统允许执行的动作边界、潜在的误用风险与隐私保护措施（可参考 ACL Ethics FAQ）；
  • 作者贡献与 AI 使用披露（Authorship & AI-Use Disclosure）：报告正文须由作者独立撰写并对其中的每一项事实、引用与实验数据负责；附录中需附上清晰的作者贡献说明（PNAS Authorship 规范）与 AI 辅助工具在代码调试、实验分析中的使用披露。

3. 三大阶段里程碑（Milestones）

整个项目按“立项提案 → 中期原型与报告 → 最终报告与系统演示”三个阶段递进推进：

里程碑一：项目提案 Proposal（第 3 周，1–2 页正文）

提案的目标是明确研究问题并证明你的技术路线切实可行。正文建议包含三个核心小节：

  1. 问题定义与动机（Problem Definition and Motivation）：你要解决什么具体问题？为什么这个问题需要复合 AI 系统或 Agent，而不能用一个简单的规则脚本或单次 LLM 调用解决？
  2. 与现有工作的对比（Comparison with Existing Work）：简要梳理相关领域的现有系统或论文，指出它们在模型能力、工具接口、数据覆盖、可靠性或评测标准上的不足。
  3. 下一步计划与评测设计（Next Steps and Evaluation Plan）：明确你将使用或收集什么数据集、计划搭建什么基线（Baseline）、采用什么评测指标，以及到中期检查前预计完成的原型目标。

里程碑二：中期原型演示与报告 Midway Report & Demo（第 7 周，3–4 页正文）

在中期阶段，你需要拥有一个已经能够端到端跑通基础流程的工作原型（Working Prototype），并完成初步的基线评测。中期交付包含两部分：

  1. 中期演示视频与代码库（Midpoint Demo Video & Repository）：录制一段展示原型实际运行过程的演示视频，并附上包含清晰 README.md 的代码仓库链接。
  2. 中期报告（Midway Report，3–4 页正文），重点包含以下四个章节：
    • 研究问题或应用规格（Research Questions / Problem Specification）：用精炼的一段话明确界定你的核心研究问题或应用目标；
    • 环境、数据与评测指标（Environment & Data）：详细说明你搭建的交互环境、工具集、测试任务集的构造过程，以及用于评判成败的定性与定量指标；
    • 方法与系统架构（Methods）：绘制系统架构图，阐述各个组件（检索、编排、记忆、优化等）的设计决策（尚未完成的高阶模块可说明具体实现计划）；
    • 当前进展、初步结果与风险分析（Summary of Progress）：展示目前已跑出的基线对比数据与至少一个具体运行案例（含失败案例初探），列出剩余周期的推进计划与潜在阻塞点。

里程碑三：最终报告与系统演示 Final Report & System Demo（期末周，8 页正文）

期末交付是一篇完整的 8 页 ICLR 格式研究/工程论文、可一键复现的最终代码仓库以及现场/录屏系统演示。最终报告的内部结构与评价权重如下：

报告章节与交付项核心内容要求分值权重（满分 25）
1. Introduction（引言）清晰界定问题背景、核心挑战、你的主要方法贡献与核心实验结论2
2. Related Work（相关工作）准确梳理相关学术文献与开源系统，明确本项目在技术脉络中的位置1
3. Environment & Data（环境与数据）完整定义任务四元组、数据采集/清洗管线、数据集统计特征与防泄漏划分1
4. Methods（方法与架构）详述系统架构、控制流、工具协议、上下文/记忆机制或优化算法的设计细节5
5. Results & Error Analysis（实验结果与错误分析）全报告最核心章节：在有代表性的任务集上对比你的系统与强基线，包含关键组件的消融实验（Ablation Studies）、成本/延迟权衡以及深入的失败轨迹归因分析10
6. Discussion & Conclusion（讨论与总结）总结系统局限性、实践经验教训与未来研究方向1
7. Reproducibility（代码可复现性）代码仓库结构整洁，README.md 提供从环境安装、配置凭据到运行最小可复现实例（Quick Start）及复现实验图表的完整命令5
必含附加声明Safety & Ethical Considerations、Authorship Statement、References、AI-Use Disclosure必含项（缺失扣分）

4. 高分项目的工程秘诀

  1. 先跑通“瘦垂直切片（Thin Vertical Slice）”，再横向扩展：在第 3–4 周先用最简单的单 Agent 基线把“数据输入 → 环境执行 → 自动评分输出”全流程跑通；有了这根标尺后，再去迭代复杂的记忆、多 Agent 或优化算法。
  2. 用消融实验（Ablations）说话：如果你声称自己设计的“双阶段检索 + 反思模块”提升了性能，不要只展示最终总分，而要展示 Base、Base + 双阶段检索、Base + 双阶段检索 + 反思 的阶梯对比，同时列出各自的 Token 消耗与耗时。
  3. 深入剖析失败案例（Failure Analysis）：一篇优秀的工程报告不仅展示系统在哪里成功，更会坦诚、深入地对失败轨迹进行分类统计并给出具体的 Transcript 案例分析——能清楚解释“为什么会失败”与“成功了”同样具有极高的学术与工程价值。
  4. 确保 Quick Start 真正一键可用：在最终提交前，在干净目录下严格按照自己写的 README.md 从头执行一遍安装与示例运行命令，确保审阅者能够在几分钟内重现你的核心演示与评分流程。
