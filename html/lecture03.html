第 03 讲｜检索增强生成（RAG）

如果直接向一个大语言模型提问：“本周哪一节助教答疑（Office Hour）排队的人最少？”没有任何外部信息源的模型只能根据训练语料中的统计常识编造一个看似合理的建议：“试试周三下午吧，通常周中人最少。”而如果系统能够先检索课程过去三周的排队日志，查出“周二下午 4 点平均排队 14 人，周四上午 9 点平均排队 3 人”，模型就能给出精准、可核查的回答：“周四上午 9 点——前面大约只有 3 名同学。”

大语言模型的参数记忆是静态且不透明的：它既不知道训练截止日期之后的实时动态，也无法访问企业的私有文档，更无法为自己凭记忆生成的数字提供可靠的原始出处。检索增强生成（Retrieval-Augmented Generation, RAG） 正是通过在推理时将外部检索器与语言模型结合，把“死记硬背”转化为“开卷查阅”。本讲将系统拆解端到端 RAG 流水线：从潜变量概率建模、文档切块与上下文增强索引，到稀疏检索（BM25）、稠密检索（DPR）、混合排序（RRF）、晚期交互重排（ColBERT），再到模型自主控制检索循环的 Agentic RAG 与三层故障诊断。

学习目标

  • 理解检索增强生成的概率建模基础（RAG-Sequence 与 RAG-Token）以及从 DrQA、REALM、DPR 到现代 RAG 的演进脉络。
  • 掌握文档切块（Chunking）、上下文增强检索（Contextual Retrieval）、晚期切块（Late Chunking）、层次化树索引（RAPTOR）与图索引（GraphRAG）的设计取舍。
  • 深入理解 HNSW 近似最近邻搜索、BM25 词频饱和公式、DPR 双编码器对比学习、RRF 混合检索以及 ColBERT 晚期交互（MaxSim）重排机制，熟练运用 Hit@k、Recall@k、MRR 与 nDCG 评估检索质量。
  • 掌握 Agentic RAG（Self-RAG、CRAG、Search-R1）的闭环决策机制，并能从检索端、阅读端与循环控制端系统诊断 RAG 故障。

知识讲解

1. 项目与检索动机

项目要从可评测问题开始

在本课程开启学期项目（Course Project）之际，首先需要确立一条贯穿始终的工程准则：任何有价值的 Agent 系统或研究项目，都必须从一个可被严格评测的问题出发。

无论是探索 Agent 在成本、延迟与安全性上的权衡、研究对提示注入与工具报错的鲁棒性、设计面向特定代码库的编程助手，还是构建自动读取课程大纲并写入日历的个人助理，单次跑通的演示（Demo）都不足以构成工程证据。在动手写复杂架构之前，必须尽早确定四件事：你的任务定义是什么、测试数据从哪里来、什么结果算成功、以及使用代码评分器（Code Graders）、LLM 裁判（LLM-as-Judge）还是人工评估来量化基线（Baselines）与失败模式。

检索为什么帮助生成

与其指望语言模型把世界上所有的知识都死记硬背到数百亿个权重参数里，不如在模型需要回答问题时，按需（Just-in-time）将最相关的参考资料提供给它。检索机制为生成模型带来了两大核心优势：

  1. 动态可更新性（Dynamic）：当公司政策修改、代码库更新或新邮件到达时，只需实时更新外部检索索引，而无需耗费巨资重新训练或微调模型权重。
  2. 可解释与可核查性（Interpretable & Verifiable）：模型可以生成指向所检索文档的明确引用（Citations），让人类用户或下游验证程序能够直接核对原文，大幅降低事实幻觉。

DrQA、REALM 与 DPR 的脉络

现代 RAG 并非凭空诞生，而是脱胎于开放域问答（Open-Domain QA）的经典 “检索器—阅读器（Retriever-Reader）” 框架：

  • DrQA（Chen et al., 2017）：面对“1933 年华沙有多少居民讲波兰语？”这类问题，先用传统的稀疏词频检索模型（TF-IDF）从维基百科全集中快速召回前 K 篇候选文档（f(D, Q) → P1, …, PK），再用在 SQuAD 阅读理解数据集上训练的双向 RNN 阅读器从文档中抽取答案片段（$833,500$）。
  • REALM（Guu et al., 2020）与 DPR（Karpukhin et al., 2020）：将检索步骤从固定的 TF-IDF 升级为基于 BERT 的可学习稠密向量检索（Dense Passage Retrieval），实现了语义层面的高效匹配。
  • RAG（Lewis et al., 2020）：将稠密检索器 DPR 与序列到序列生成模型 BART 端到端结合，正式确立了“检索增强生成”这一范式。

2. 原始 RAG 模型

把文档当作潜变量

在 Lewis et al.（2020）提出的原始 RAG 数学框架中，给定用户输入 x，检索到的相关文档段落 z 被建模为一个潜变量（Latent Variable）。系统包含两个概率组件：

  1. 检索器（Retriever）p_η(z \mid x)：给定查询 x，返回与查询最相关的前 K 个文档段落及其概率分布；
  2. 生成器（Generator）p_θ(yi \mid x, z, y1:i-1)：同时以查询 x、检索到的段落 z 以及前序已生成词元为条件，逐 Token 预测输出答案 y。

为了根据 x 生成完整答案 y，模型在 Top-K 检索候选集合上对潜变量 z 进行边际化求和（Marginalization）：按检索器认为每篇文档相关的概率，对各文档生成的答案概率进行加权汇总。

RAG-Sequence 与 RAG-Token

根据边际化求和发生粒度的不同，原始 RAG 提出了两种变体：

  • RAG-Sequence（序列级边际化）：假设整段回答 y 由同一篇潜在文档支撑。模型先针对每一篇候选文档 z 独立生成完整的序列概率，最后在序列层面加权求和：
    pRAG-Sequence(y \mid x) ≈ ∑z ∈ top-k(p(· \mid x)) p_η(z \mid x) ∏i=1N p_θ(yi \mid x, z, y1:i-1)
  • RAG-Token（词元级边际化）：允许模型在生成同一个回答的不同 Token 时，动态参考不同的检索文档。模型在预测每一个 Token yi 时都对所有候选文档边际化求和，再将各步概率相乘：
    pRAG-Token(y \mid x) ≈ ∏i=1N ∑z ∈ top-k(p(· \mid x)) p_η(z \mid x) p_θ(yi \mid x, z, y1:i-1)

这种区分非常直观地揭示了多源信息综合的机制：当答案完整存在于单篇文档中时，序列级一致性更好；而当一句回答的前半句需要引用文档 A、后半句需要结合文档 B 时，Token 级混合则提供了跨文档拼图的灵活性。

DPR 与 BART 的组合

在具体实现中，检索器 p_η(z \mid x) ∝ exp(d(z)^⊤ q(x)) 采用双编码器架构：文档编码器 d(z) = BERTd(z) 预先将所有知识库文档编码为向量，查询编码器 q(x) = BERTq(x) 实时编码用户问题，并通过最大内积搜索（Maximum Inner Product Search, MIPS） 找出得分最高的 K 个段落；生成器则将 x 与 z 拼接后输入给编码器—解码器模型 BART。在训练时，系统直接最小化目标答案的负边际对数似然 ∑j -log p(yj \mid xj)，无需任何人工标注“哪篇文档应该被检索出来”，即可端到端微调查询编码器与生成器。

原课评测与 RAG 变体

在 Natural Questions（NQ）、TriviaQA、WebQuestions 和 CuratedTrec 等开放域问答基准上，RAG 显著超越了仅靠参数记忆的闭卷大模型与传统抽取式问答系统；在 Jeopardy 问题生成任务的人工盲测中，RAG 生成的内容在事实准确性（Factuality）与具体性（Specificity）上也大幅胜出。随着大模型上下文能力的演进，现代工程实践中更常将检索出的 Top-K 段落直接拼接到单个 Decoder-only LLM 的提示词中（In-Context RAG），并在其基础上衍生出查询改写、多路路由、重排序与迭代自省等丰富的系统变体（Gao et al., 2024）。

3. 表示、切块与组织

Embedding 的不同粒度

构建高质量向量检索器的前提是选择合适的稠密向量表征（Embeddings）。不同历史阶段与任务场景的编码器覆盖的语义粒度各不相同：

向量类型代表模型单个向量表征的对象适用场景
静态词向量（Static Word）word2vec, GloVe词表中的一个独立词型（不论上下文）早期词汇相似度匹配
上下文化词元向量（Contextual Token）BERT, RoBERTa特定句子语境下的单个 Token命名实体识别、序列标注、ColBERT 晚期交互
段落/文本块向量（Passage / Chunk）Sentence-BERT, DPR, E5, BGE整段文本或文档切块（Chunk）主流 RAG 稠密向量检索
多模态共享空间向量（Multimodal）CLIP, SigLIP文本或图像（映射至同一向量空间）跨模态图文检索
图结构向量（Graph）node2vec, GNN Encoders图中的节点或关系边知识图谱与社交网络检索

在段落检索中，我们将每个文档切块映射为固定维度的向量，并通过余弦相似度（Cosine Similarity）或向量内积（Inner Product）衡量查询与文档块的匹配程度。

Chunking 的边界与元信息

我们不能把一本几百页的手册压成一个向量，因此文档切块（Chunking）是索引构建的第一道关键工序：

  • 固定大小切块（Fixed-size Chunking）：通常以 100–500 Tokens 为一个切块单位，并设置 10%–20% 的滑动窗口重叠（Overlap）。切块太小会导致句子缺乏上下文背景，切块太大则会把多个无关主题平均在同一个向量里稀释关键信号；而设置重叠是为了防止关键句子恰好在切块边界处被拦腰截断（例如前一块末尾停在 "The project milestone is due Week 6, Thursday"，后一块开头变成 "11:59pm. Late days may not be applied..."）。
  • 语义与结构切块（Semantic / Structure Chunking）：按照 Markdown 标题、章节、自然段落或语义断点切分，保持逻辑单元完整，同时在每个块中附带所属章节标题、文档 ID 与更新时间等元数据。

Contextual retrieval

即便按自然段落切块，脱离了全文的孤立段落依然经常出现指代不明的问题。来看课件中的一个典型反例：

用户查询：“ACME 公司在 2023 年第二季度的营收增长率是多少？” 原始切块（Chunk）：“该公司营收较上一季度增长了 3%。”

如果只对“该公司营收较上一季度增长了 3%”这句话建索引，它既不包含“ACME 公司”，也不包含“2023 年 Q2”，无论是向量检索还是关键词检索都会彻底漏掉它！

Anthropic 提出的上下文增强检索（Contextual Retrieval）给出了简洁高效的解法：在构建索引时，将整篇文档与当前切块一起传给语言模型，让模型生成一句简短的背景说明前缀（例如：“摘自 ACME 公司 2023 年 Q2 SEC 财报；2023 年 Q1 营收为 3.14 亿美元。”），将其拼接到原始切块前面后再进行向量化与 BM25 索引。实验表明，结合 Contextual Embeddings 与 Contextual BM25 能将检索失败率大幅降低。

Late chunking

Contextual Retrieval 虽然有效，但需要为每个切块额外调用一次生成模型并增加了索引 Token 数。有没有不需要生成前缀的替代方案？晚期切块（Late Chunking, Günther et al., 2024） 提出了“先全文编码，再按区间池化”的思路：

  1. 先用支持长上下文的双向编码器（如长上下文 Embedding 模型）一次性读取整篇完整文档，由于自注意力覆盖全文，此时每个 Token 的输出向量都已经自然融合了整篇文档的上下文信息（包括前文提到的公司名与财报季度）；
  2. 然后再按照每个切块的起止 Token 边界，对相应区间内的 Token 向量做均值池化（Mean Pooling），得到每个切块的最终向量。

Late Chunking 与 Contextual Retrieval 目标一致，但实现路径完全不同：前者通过长上下文编码器的注意力层在向量表征内部注入全文语境，零额外生成开销；后者则通过显式生成文本前缀同时服务于向量检索与词法检索。

RAPTOR

当用户提出的问题跨越整篇长文档（例如针对《灰姑娘》全书提问：“这个故事的核心主题是什么？”或“她是如何迎来美好结局的？”），仅靠底层零散的叶子切块很难拼凑出全局脉络。RAPTOR（Sarthi et al., 2024） 通过自底向上构建层次化摘要树解决了这一难题：

  1. 将原始文档切块作为树的叶子节点并计算向量；
  2. 对向量进行聚类（Clustering），并用 LLM 为每个簇生成一段高层摘要；
  3. 将生成的摘要再次编码、聚类并生成更高层的摘要，直至根节点；
  4. 在检索时，系统同时在所有层级的节点中搜索——局部细节问题会自然命中底层的叶子切块，而宏观主题问题则会命中高层的聚类摘要节点。

GraphRAG

对于需要跨多篇文档梳理实体关联与全局结构的复杂查询，微软提出的 GraphRAG（Edge et al., 2024） 进一步用 LLM 从文档库中抽取出实体（Entities）与关系（Relationships）构建知识图谱，利用图社区发现算法（如 Leiden 算法）将紧密关联的实体划分为不同层级的社区（Communities），并预先生成每个社区的摘要报告，从而支持跨实体的多跳推理与全局总结。

4. 索引与检索算法

Exact search 与 ANN

当文档库包含 N 个 d 维切块向量时，最朴素的精确最近邻搜索（Exact Search / Brute-force Scan）需要计算查询向量与所有 N 个向量的内积，单次查询时间复杂度为 O(N · d)。当 N 达到数百万甚至上亿规模时，暴力扫描无法满足实时交互要求。

因此，工业界普遍采用近似最近邻搜索（Approximate Nearest Neighbor, ANN），用极小比例的召回率损失换取数量级的速度提升，主流方法包括三类：

  • 倒排文件索引（IVF, Inverted File Index）：先用 K-Means 将向量空间划分为多个聚类中心（Centroids），查询时只扫描距离查询向量最近的少数几个簇；
  • 乘积量化（PQ, Product Quantization）：将高维浮点向量拆分为多个子向量并量化为短编码，大幅压缩内存占用并加速距离估算；
  • 分层可导航小世界图（HNSW, Hierarchical Navigable Small World）：目前最主流的高性能内存图索引结构。

HNSW 的插入与搜索

HNSW 的核心思想就像交通网络中的“高铁—城际—地铁”分层导航：

  • 多层图结构：第 $0$ 层（最底层）包含全部 N 个向量节点，连接密集；往上每一层以指数衰减的概率随机抽取少数节点保留，越往顶层节点越稀疏，边跨越的几何距离越远。
  • 贪心搜索过程：当一个查询向量进来时，从最顶层的入口节点出发，在当前层每次贪心地跳向距离查询更近的邻居节点；当在当前层达到局部最近点无法继续前进时，就下降一层继续贪心微调，直到在第 $0$ 层精细搜索出 Top-k 最近邻。全过程平均只需约 O(log N) 次跳转。
  • 构图防陷机制：在逐个插入新向量构图时，系统会随机决定该节点能到达的最高层级，并在每一层不仅连接最近的 M 个邻居，还会按启发式规则保留跨簇的长距离连边，防止贪心搜索在局部孤岛中陷入死胡同。

BM25 的组成

尽管稠密向量检索发展迅猛，但在工程实践中，最经典、最不可或缺的检索基石依然是基于倒排索引（Inverted Index）的词法检索算法 BM25（Best Matching 25）。

给定包含词元 q1, …, qn 的查询 Q 与文档 D，BM25 的打分公式由三部分精妙配合而成：

score(D, Q) = ∑i=1n IDF(qi) · f(qi, D) · (k1 + 1)f(qi, D) + k1 · (1 - b + b · |D|avgdl)
  1. 逆文档频率 IDF(qi)：衡量查询词 qi 在整个语料库中的稀有程度。像 "the"、"email" 这样几乎每篇文档都出现的常见词权重极低，而特定项目代号、人名或错误码等稀有词则拥有极高权重。
  2. 词频饱和（Term Frequency Saturation，由 k1 控制，通常取 1.2 \sim 2.0）：传统 TF-IDF 中词频 f(qi, D) 是线性增长的，一篇把某关键词重复 50 次的垃圾文档得分会是出现 5 次文档的 10 倍。而在 BM25 的分式 f · (k1 + 1)f + k1 · (…) 中，随着 f → ∞，这一项会渐近收敛于上界 k1 + 1，从而防止单个词的高频堆砌绑架总分。
  3. 文档长度归一化（Length Normalization，由 b ∈ [0, 1] 控制，通常取 $0.75$）：长文档天然包含更多词汇，更容易碰巧命中查询词。比值 |D|avgdl 将当前文档长度 |D| 与语料库平均文档长度 avgdl 对比：若文档比平均长度更长，分母中的惩罚项变大，从而公平拉平长短文档的得分起跑线。

BM25 公式与版本差异

在编写代码实现 BM25（例如在 HW1 第 3 题中）时，需要特别注意 IDF(qi) 的两个常见公式变体：

  • 经典 Robertson-Spärck Jones 原始形式（课件展示形式）：
    IDFclassic(qi) = ln N - n(qi) + 0.5n(qi) + 0.5

    其中 N 为文档总数，n(qi)（即 df）为包含词元 qi 的文档数。注意当一个词出现在超过一半的文档中（n(qi) > N/2）时，该式对数内部小于 $1$，计算出的 IDF 会变成负数。

  • Lucene / 现代工程非负形式（HW1 采用的标准形式）：
    IDFLucene(qi) = ln (1 + N - n(qi) + 0.5n(qi) + 0.5)

    通过在真数中加 $1$，保证了任何词元的 IDF 严格非负。在工程实现与单元测试中，务必严格对齐接口规范所指定的公式与分词器。

DPR 的训练

为什么我们需要在 BM25 之外训练稠密检索器 DPR（Dense Passage Retrieval, Karpukhin et al., 2020）？因为 BM25 完全依赖字面词元重叠（Word-overlap）：如果用户搜 "Who is the bad guy in Lord of the Rings?"，而文档里写的是 "Sauron is the main antagonist..."，由于 "bad guy" 与 "antagonist" 没有任何共同字母，BM25 得分为零。

DPR 使用两个独立的 BERT 编码器分别将问题与段落映射为低维稠密向量，并使用对比学习（Contrastive Loss）进行训练：拉近问题 q 与正样本段落 p+ 的内积相似度，同时推远与负样本段落 p- 的相似度。DPR 成功的关键工程诀窍在于负样本的构造：除了利用同一个训练批次内其他问题的正样本作为免费负样本（In-batch Negatives），还专门加入了一批 BM25 难负样本（BM25 Hard Negatives）——即字面与问题高度重合（BM25 得分很高）、但实际上并不包含正确答案的段落。这迫使编码器不能偷懒只做浅层关键词匹配，而必须学会深层语义甄别。

命中与排序指标

为了科学评估一个检索器的好坏，我们需要根据下游使用场景区分两类核心指标（设测试查询集为 Q，查询 q 的真实相关文档集合为 Rq，检索器返回的前 k 个文档集合为 Topk(q)）：

  1. 命中与召回指标（不敏感于前 k 名内部的具体位次）：
    • Hit@k（命中率）：前 k 个结果中至少包含一篇相关文档的查询比例：
    Hit@k = 1|Q| ∑q ∈ Q 𝟙[Rq ∩ Topk(q) ≠ ∅],   Failed@k = 1 - Hit@k
    • Recall@k（召回率）：前 k 个结果找回的相关文档占该查询全部相关文档的比例：
    Recall@k = 1|Q| ∑q ∈ Q |Rq ∩ Topk(q)||Rq|
  1. 顺序敏感指标（越靠前权重越高）：
    • MRR@k（平均倒数排名，Mean Reciprocal Rank）：关注第一篇相关文档出现的排名 rankq（若未出现在前 k 名则记为 $0$）：
    MRR@k = 1|Q| ∑q ∈ Q 1rankq
    • nDCG@k（归一化折损累计增益）：当不同文档具有多级相关度得分 relq, i 时，按位置对数折损累加 DCGq@k = ∑i=1k \frac{relq, i}{log2(i + 1)}，再除以理想最优排序下的 IDCGq@k 进行归一化。

DPR 实验的适用边界

Karpukhin et al.（2020）的实验表明，仅需约 1,000 对问答训练样本，微调后的 DPR 就能在开放域问答的 Top-k 准确率上超越 BM25，并在 Natural Questions、TriviaQA 等 5 个数据集中的 4 个上显著领先。不过在只包含极少训练样本且高度依赖专有名词精确匹配的数据集（如 SQuAD）上，BM25 依然极具竞争力。

Hybrid search 与 RRF

既然 BM25 擅长精确匹配专有名词、产品编号、错误码与罕见字面词，而稠密向量检索擅长处理同义替换与语义改写，最稳健的工程方案就是将两者结合起来做混合检索（Hybrid Search）。

但 BM25 输出的是无上界的词频对数得分（可能从 $0$ 到 30+），而向量检索输出的是 [-1, 1] 之间的余弦相似度，量纲完全不同，直接加权求和需要针对每个数据集繁琐地调节超参数。为此，工程界广泛采用无需调参的 倒数排名融合（Reciprocal Rank Fusion, RRF）：完全忽略原始分数，仅根据文档 d 在各个检索器 r ∈ R 返回列表中的名次 rankr(d) 进行融合：

RRF(d) = ∑r ∈ R 1k + rankr(d)   (通常取常数 k = 60)

常数 k = 60 平滑了头部排名的极端差距，使得在两个检索器中都排在前列的文档能够稳居榜首，同时兼收单边检索器排在第一名的强匹配结果。

5. 重排与 ColBERT

Bi-encoder 与 cross-encoder

在神经检索架构中，计算效率与交互深度之间存在着根本矛盾：

  • 双编码器（Bi-encoder，如 DPR）：查询 q 和文档 d 各自独立通过编码器变成单个向量，最后只做一次点积。优点是所有文档向量均可离线预先算好存入索引，线上查询只需几十毫秒；缺点是查询中的词与文档中的词在编码过程中完全没有发生注意力交互，细粒度匹配信息被压扁在了一个向量里。
  • 交叉编码器（Cross-encoder，如 BERT Reranker）：将查询和候选文档拼接成 [CLS] q [SEP] d [SEP] 一起送入 Transformer，让查询的每一个 Token 与文档的每一个 Token 在每一层都进行全注意力交互。准确率极高，但由于无法预计算文档向量，对 1,000 篇候选文档打分就需要实时跑 1,000 次完整的 BERT 前向传播（耗时可达数秒至十余秒），根本无法直接扫描全库。

因此，标准工业级流水线通常采用“两阶段检索（Retrieve-then-Rerank）”：第一阶段用快速的 Bi-encoder + BM25 从百万级文档中召回 Top-100 候选，第二阶段再用精细的 Cross-encoder 对这 100 个候选重排序（Reranking），选出最终的 Top-10 交给 LLM。

Late interaction / MaxSim

有没有一种架构，既能像 Bi-encoder 一样离线预计算文档表征，又能像 Cross-encoder 一样保留 Token 级别的细粒度交互？斯坦福提出的 ColBERT（Khattab & Zaharia, 2020） 给出了晚期交互（Late Interaction）的优雅方案：

  1. 文档编码器依然离线独立处理每篇文档，但不再把整篇文档池化成一个向量，而是保留文档中每一个 Token 的上下文化输出向量 {d1, …, dm}；
  2. 查询编码器在线独立将查询编码为 Token 向量序列 {q1, …, ql}；
  3. 在打分阶段，通过无参数的 最大相似度求和算子（MaxSim） 进行交互：对于查询中的每一个词元 qi，在文档的所有词元向量中找出内积最大的一项，再对所有查询词元求和：
    Sq, d = ∑i ∈ q maxj ∈ d ( qi · dj )

MaxSim 算子极其轻量且支持向量索引加速，它精准刻画了“查询中的每一个关键概念，是否在文档中找到了最匹配的对应词元”。

公平的速度比较

下表汇总了四类检索器在预计算机制、延迟量级与优劣边界上的工程对比（以 MS MARCO 基准上的典型量级为例）：

检索器架构离线预计算内容典型查询延迟核心胜出场景主要局限与代价
BM25（稀疏检索）倒排索引（Inverted Index）\sim 60 ms（极快）专有名词、ID、错误码等精确字面匹配无法识别同义词与句式改写
DPR（双编码器）每篇文档段落 1 个稠密向量数十毫秒（极快）大规模语料上的语义相似匹配压缩成单向量丢失细节，对罕见字面词弱

6. Agentic RAG 与失败分析

谁决定查什么和何时停止

前面讨论的传统 RAG 流水线都是“一锤子买卖”：无论用户问什么，固定检索一次 Top-k，塞进提示词生成答案就结束。然而在复杂任务中（例如 HW1 第 4 题的多跳邮件问答：“负责 Foxglove 项目的那位经理，他的备用审批人是谁？”），第一轮检索只能查出“负责 Foxglove 项目的经理是 Alice”，必须根据第一轮阅读的结果，发起第二轮查询“Alice 的备用审批人”才能找到最终答案。

Agentic RAG 将检索器封装为 Agent 循环中的一个可调用动作（Action），把三项核心控制权交还给模型：

  1. 是否需要检索（When to retrieve）：常识问题直接回答，缺事实证据时才触发检索；
  2. 如何构造与改写查询（What query to issue）：将复杂的原始问题拆解为精准的子查询，并在首轮未命中时换用同义词或提取出的新实体追查；
  3. 何时停止检索（When to stop）：判断当前收集到的证据是否已经足以回答问题，或者在达到预算上限（如最多 3 次检索）时终止循环。

Self-RAG

Self-RAG（Asai et al., 2024） 通过在模型词表中引入特殊的控制与自省词元（Reflection Tokens），训练单个语言模型在生成过程中自主完成“按需检索—自我评估—生成回答”的闭环：模型先生成 Retrieve 标记决定是否需要检索；读入多篇候选段落后，依次生成 IsRel（段落是否相关）、IsSup（生成内容是否有据可查）与 IsUse（回答整体是否有用）等自省评分，从而在解码阶段自动过滤无关噪声并确保事实可溯源。

CRAG 与 Search-R1

为了进一步提高多步检索的鲁棒性，两条代表性技术路线值得关注：

  • 纠错式 RAG（CRAG, Yan et al., 2024）：引入一个轻量级的检索评估器（Retrieval Evaluator）对召回文档的相关性置信度打分，按得分高低触发三种不同动作——高分（Correct）则精炼提取关键句；低分（Incorrect）则丢弃原结果并改用外部网页搜索；居中（Ambiguous）则结合两者。
  • 强化学习训练搜索策略（Search-R1, Jin et al., 2025）：不再手工编写复杂的启发式重搜规则，而是直接在多轮搜索交互环境中，利用最终答案是否正确的可验证奖励（RLVR），通过强化学习端到端优化模型的 <think> ... <search> query </search> <information> ... </information> ... <answer> 推理与搜索轨迹。

三层故障诊断

当一个 RAG 或 Agentic RAG 系统给出了错误答案时，切忌盲目修改提示词。工程上应当按照检索端（Retrieval-side）、阅读端（Reader-side）与循环端（Loop-side）三层分类法逐层排查：

故障层级典型失败模式现象与机理工程排查与修复策略
检索端（Retrieval-side）1. 召回上限（Recall Ceiling）
2. 索引过期（Stale Index）
3. 权限越界（Permission Leak）		关键证据根本不在返回的 Top-k 中；文档已更新但旧向量未刷新；检索出了当前用户无权访问的机密文档。单独统计检索器的 Recall@k；采用 BM25 + 稠密向量的 RRF 混合检索；在索引层强制绑定文档 ACL 权限过滤与版本时间戳。
阅读端（Reader-side）1. 中间迷失（Lost in the Middle）
2. 相似干扰（Distraction）
3. 证据冲突（Evidence Conflict）		正确文档明明在 Top-k 中，但位于长上下文中部被模型忽略；被字面相似但对象不同的干扰文档误导；新旧两版政策同时进入上下文导致模型混淆。引入 Reranker 缩减送入 LLM 的文档数并将高置信文档置于首尾；在切块中显式保留文档发布日期与生效状态（Contextual Retrieval）。
循环端（Loop-side）1. 误差累积（Compounding Error）
2. 缺乏终止规则（No Stopping Rule）
3. 提示注入（Prompt Injection）		第一跳提取错了人名导致后续查询全偏；反复用相同关键词死循环搜索耗尽预算；被检索文档中夹带的恶意指令劫持。强制设定最大搜索步数（如 max_searches=3）与重复查询拦截；对检索出的外部文本做严格的上下文边界隔离，仅将其视为不可信证据。
