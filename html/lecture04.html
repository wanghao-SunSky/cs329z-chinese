第 04 讲｜工具使用与函数调用

在上一讲中，我们看到检索增强生成（RAG）能够为大语言模型补充外部静态或动态文档。但如果用户问的是：“17,423 × 892 等于多少？”或者“帮我查一下斯坦福现在的实时气温，并在我的日历上把今天下午 3 点的会议推迟半小时”，光靠检索文档就无能为力了。

大语言模型本质上是基于统计关联的序列预测器：它在多位数算术、长链条符号逻辑推导与动态规划问题上准确率随规模急剧下跌；它无法获知此时此刻的股票价格或传感器读数；它更无法仅凭输出一段文字就自动修改外部数据库或操作物理世界。工具使用与函数调用（Tool Use & Function Calling） 正是赋予语言模型“双手”的关键桥梁。本讲将在收尾 RAG 长上下文与引用局限的基础上，系统探讨模型如何通过自监督与指令微调学会使用成千上万个工具（Toolformer、ToolkenGPT、ToolLLM、Gorilla），剖析从 REST API、Function Calling 到模型上下文协议（MCP）的三代接口标准，并掌握 BFCL、ToolBench 与 τ-bench 等工具评测方法。

学习目标

  • 理解长上下文 RAG 的性能饱和现象、中间迷失效应与引用幻觉（Citation Hallucination）诊断指标，明确引入外部工具的三大核心动因。
  • 掌握让语言模型学会调用工具的四种代表性训练范式：Toolformer 的自监督损失过滤、ToolkenGPT 的专用词元嵌入、ToolLLM 的大规模 API 检索微调，以及 Gorilla 的检索感知训练与 AST 幻觉评测。
  • 深入理解三代工具接口标准（REST API、JSON Schema Function Calling、MCP 协议）的架构演进，掌握 MCP 的能力发现（tools/list）、调用执行（tools/call）与双向鉴权边界。
  • 掌握工具调用系统的评测维度（BFCL、ToolBench、τ-bench）与可靠性指标（pass@k 与 passk），能够系统识别并防御单步、多步与交互层面的工具故障。

知识讲解

1. RAG 收尾与工具动机

检索规模与收益饱和

既然现代大语言模型支持数万乃至数十万 Token 的上下文窗口，在做 RAG 时，我们能不能干脆每次把检索出来的前 100 篇文档全部塞给模型？

实验数据给出了否定的答案：

  1. 注意力退化与“中间迷失”（Lost in the Middle, Liu et al., 2023）：当把包含正确答案的那篇关键文档混入 20 篇干扰文档中时，如果关键文档放在提示词的最开头或最末尾，模型准确率较高；但一旦关键文档落在了上下文的中间位置，模型的问答准确率甚至会跌破完全不给任何文档的闭卷基线（例如在实验中，GPT-3.5-Turbo 闭卷准确率为 56%，只给唯一正确文档的 Oracle 准确率高达 88.5%，而把正确文档埋在 20 篇文档中间时准确率反而低于闭卷水平）。
  2. 收益快速饱和：随着检索文档数量 k 增加，检索器的召回率（Recall）虽然缓慢爬升至 90%，但下游模型的最终问答准确率在 10 \sim 20 篇文档之后便迅速饱和甚至开始下降。过多的次相关文档不仅消耗海量 Token 预算，还会严重干扰模型的注意力分配。

引用与长上下文诊断

RAG 的核心卖点之一是让模型生成带引用标记（如 [1], [2]）的回答。然而，引用标记本身也是由语言模型自回归生成的，这意味着引用同样会发生幻觉（Citation Hallucination）。Liu et al.（2023）对商业生成式搜索引擎的评测发现，虽然模型生成的回答读起来非常流畅、在人工主观有用性评分（1–5 分）上得分很高，但其引用的客观质量却不容乐观，需要用两个正交指标严格检验：

  • 引用精确率（Citation Precision）：在模型已经标注的所有引用 [i] 中，对应的第 i 篇文档真正能够支持该句陈述的比例（排查“乱贴无关标签”）；
  • 引用召回率（Citation Recall）：在回答所有需要事实支撑的陈述句中，所附带的引用文档合集能够完全覆盖并证明该陈述的比例（排查“漏标出处或无中生有”）。

此外，在评估长上下文能力时，像 大海捞针（Needle-in-a-Haystack） 这样的测试虽然能检验模型从长文中定位单句事实的能力，但“找出一根针”的成功并不代表模型能够在长上下文中完成跨多处的复杂推理与计算。

工具弥补能力与访问边界

跳出纯文本检索，大语言模型在三类根本性边界上必须借助外部工具（Tools）：

大语言模型的固有局限具体表现场景外部工具提供的解决方案
1. 无法精确计算的确定性任务（What LLMs can't compute）多位数乘法、多步符号逻辑推导（如斑马谜题）、动态规划（Dziri et al., 2023 证明随着问题规模增加，零样本准确率迅速归零）计算器（Calculator）、Python 代码解释器、符号求解器与形式化验证器
2. 训练语料未曾涵盖的知识（What LLMs never saw）长尾生僻事实、训练截止日期后的实时动态、企业内部私有数据库Web 搜索引擎、实时新闻/行情 API、内部语料库检索工具
3. 语言之外的外部世界与状态（What LLMs can't reach）外部软件接口、数据库写入、物理世界交互、当前精确时间与传感器状态函数调用（Function Calling）、MCP 服务、浏览器自动化、系统时钟

完整工具链

从系统视角来看（Wang et al., 2024），一个供语言模型使用的工具（Tool）是运行在模型外部的计算机程序的函数接口。一次完整的工具使用闭环包含四个严格步骤：

  1. 模型生成调用指令：例如面对 "What is 17,423 × 892?"，模型不直接硬猜数字，而是输出结构化指令 calculate(17423 * 892)；
  2. 宿主程序拦截并执行：外部运行时（Harness）解析出函数名与参数，调用真正的计算器程序；
  3. 返回环境观测：计算器算出精确结果 15,541,316 并交回给宿主程序；
  4. 结果重入上下文：宿主程序将结果写入上下文，模型据此生成最终回答 "It is 15,541,316"。

2. 怎样让模型学会工具

Toolformer 的五类工具

在早期基础模型尚未原生内置工具能力时，如何让一个普通预训练语言模型（如 60 亿参数的 GPT-J）无需大量人工标注就能自己学会调用工具？Toolformer（Schick et al., 2023） 开创了基于自监督学习的经典范式，涵盖了五类基础工具：问答系统（QA）、计算器（Calculator）、维基百科搜索引擎（WikiSearch）、机器翻译系统（MT）与日历（Calendar）。

采样—执行—过滤—训练

Toolformer 的核心思想是在海量普通无标注文本（如 CCNet）中，让模型自己尝试“插入”API 调用，并只保留那些执行结果真正有助于预测后续文本的调用。全流程分为四步：

  1. 采样 API 调用（Sample API Calls）：给模型提供少量手工编写的上下文示例（Few-shot Prompt），让模型在普通文本句子（如 "Pittsburgh is known as the Steel City."）中找出适合插入 API 调用的位置 i（满足触发概率 pi > τs），并采样生成 m 个候选调用（如 [QA("What other name is Pittsburgh known by?")]）。
  2. 执行 API 调用（Execute API Calls）：真实调用外部程序执行这些候选请求，获取返回的字符串结果（如 "The Steel City"）。
  3. 基于损失过滤（Filter API Calls）：这是最关键的一步——判断这次工具调用到底有没有用。
  4. 微调模型（Finetune）：将通过过滤的 [API调用 → 返回结果] 保留在原文本中构成增强数据集，微调语言模型本身。

以未来损失衡量帮助

Toolformer 如何定量判断一次 API 调用“有用”？它计算模型在插入 API 位置之后的未来 Token 序列上的加权交叉熵损失（Weighted Cross-Entropy Loss, Li），并对比两种情况：

  • 包含完整调用与真实返回结果时的后续预测损失：Li+ = Li(含 API 调用与返回结果 ri)；
  • 完全不调用 API 与 只放 API 调用但不给返回结果 两种基线中的较小损失：Li- = min(Li(ϵ), Li(仅 API 调用无结果))。

只有当真实返回结果使后续文本的预测损失显著降低——即差值 Li- - Li+ ≥ τf（超过过滤阈值 τf）时，这条工具调用才会被保留下来！例如，查出 "Pittsburgh" 的别名 "Steel City" 能直接让模型零损耗地预测出后文的 "the Steel City"，因此获得高分保留；而如果调用返回的结果对下文预测毫无帮助，就会被自动剔除。通过这一机制，微调后的 6B Toolformer 在事实补全、数学、时间问答等任务上甚至超越了不带工具的 175B GPT-3。

ToolkenGPT：把工具变成 token

Toolformer 证明了自监督工具学习的可行性，但它需要微调模型全部参数，且只能处理屈指可数的几个工具。当工具数量扩大到几百个时，能不能不微调大模型本体，而是像扩充词表一样，把每一个工具表示为一个专门的新词元（"Toolken"）？

ToolkenGPT（Hao et al., 2023） 提出了这一巧妙设计：

  • 冻结预训练大模型的主干权重，只为每个工具学习一个专门的词元嵌入向量（Toolken Embedding，打包在矩阵 W_τ 中），将其拼接到原有的词表分类头之后；
  • 在正常文本生成过程中，一旦模型预测出的下一个 Token 是某个工具词元（例如 [square]），生成立即暂停并切换到“工具参数填充模式（Tool-mode prompt）”，利用少样本示例填入参数并执行工具，随后将返回值重新送回主上下文继续推理；
  • 在训练 W_τ 时，对于句子 "the area is 256 square feet"，训练目标只需在第一个结果数字 2 的位置预测工具词元 [square]，而将后续结果数字 5、6 标记为 [N/A] 跳过损失计算：
    L(W_τ) = ∑(s, s') ∈ D ∑i=1N -log P(t'i \mid t<i) · 𝟙[t'i ≠ N/A]

    这样只需极小的训练开销即可扩展到 234 个算术、知识与机器人控制工具。

ToolLLM / ToolLLaMA

当工具规模从百级进一步跃升到上万个真实世界的 REST API（如 RapidAPI 平台上的 16,000+ 个 API）时，既不可能把所有工具塞进提示词，也不可能靠简单词元区分。ToolLLM（Qin et al., 2023） 构建了完整的工业级链路：

  1. 从 RapidAPI 收集覆盖数千个工具的 16,464 个真实 API，并用 ChatGPT 合成涵盖单工具与多工具组合的复杂用户指令与深度优先搜索（DFSDT）调用轨迹（构成 ToolBench 数据集）；
  2. 训练一个专门的神经 API 检索器（Neural API Retriever），根据用户指令从上万个 API 中精准召回最相关的 Top-K 个候选 API 文档；
  3. 在召回的 API 文档与多步轨迹上微调 LLaMA，得到 ToolLLaMA。

Gorilla 与 retrieval-aware training

在面对海量且频繁更新的机器学习与云计算 API 时，Gorilla（Patil et al., 2023） 从 HuggingFace Hub、PyTorch Hub 与 TensorFlow Hub 收集了 1,645 个 API 规范，并用 GPT-4 通过 Self-Instruct 生成了指令—代码配对数据。

Gorilla 揭示了一个极具实战价值的训练洞见——检索感知训练（Retrieval-Aware Training, RAT）：

  • 如果模型在微调时只练习“闭卷生成 API 调用（Zero-shot）”，到了线上给它拼入实时检索出的 API 文档时，它往往不会利用文档，甚至会被低质量检索结果带偏；
  • 反之，如果在微调阶段就将检索出的参考文档放入上下文，并且刻意在训练数据中混入一部分检索正确的文档和一部分检索错误的干扰文档，模型就能学会两项关键本领：当检索出的 API 文档相关时严格照章调用（适应 API 更新）；当检索器召回了一篇无关文档时，果断忽略干扰，依靠自身参数知识正确作答。

API 幻觉与规模比较

为了精确诊断模型在生成工具调用代码时是否编造了不存在的函数名或参数，Gorilla 引入了抽象语法树子树匹配（AST Sub-Tree Matching）：将模型生成的代码解析为 AST 语法树，与标准 API 库中的函数签名树进行结构比对，从而严格区分“调用了完全不存在的虚构 API（Hallucination）”与“选对了 API 但填错了参数”。

3. 从 REST 到 MCP

REST / HTTP 接口

靠每新出一个 API 就重新微调一次模型显然无法适应瞬息万变的软件生态。因此，工程界的核心思路从“改变模型以适应工具”转向了“标准化工具的描述方式，使任何模型都能在运行时零样本调用”。

这一演进经历了三代接口标准：

  1. 第一代：面向人类开发者的 REST API：通过 HTTP 动词（GET 读取、POST 创建、PUT 更新、DELETE 删除）和 URL 路径（如 GET https://api.weather.com/v1/current?city=Stanford）暴露服务。REST 是为人类程序员阅读文档编写代码设计的，缺乏统一的机器可读调用契约，直接让模型手写原始 HTTP 请求极易出错。

Function calling 与 schema

  1. 第二代：面向模型的函数调用（Function Calling）：宿主程序在上下文中为每个工具提供结构化的 JSON Schema，明确声明函数名（name）、功能描述（description）、参数字段类型（properties）与必填项（required）：
JSON
{
  "name": "get_weather",
  "description": "获取指定城市的实时天气",
  "parameters": {
    "type": "object",
    "properties": {
      "city": { "type": "string" }
    },
    "required": ["city"]
  }
}

模型只需输出符合该 Schema 的 JSON 调用对象 {"name": "get_weather", "arguments": {"city": "Stanford"}}，由宿主程序完成参数验证与实际分发执行。然而，Function Calling 的局限在于工具定义紧耦合在每个应用各自的代码库里——你在应用 A 里写好的 GitHub、Slack 或数据库连接器，换到应用 B 或另一个 IDE 里又得重新封装一遍。

MCP 的角色

  1. 第三代：面向生态系统的模型上下文协议（Model Context Protocol, MCP）：为了解决“M 个 AI 应用与 N 个外部数据源之间需要编写 M × N 个定制适配器”的碎片化困境，MCP 制定了一套统一的开放协议，将系统划分为三个标准角色：
    • MCP Host（宿主应用）：运行大语言模型并管理用户交互的主程序（如 Claude Desktop、Cursor IDE 或你编写的 Agent 应用）；
    • MCP Client（客户端）：驻留在宿主应用内部，负责与对应的 MCP Server 维护一对一的协议连接；
    • MCP Server（服务端）：封装特定外部系统（如本地文件系统、PostgreSQL、Google Drive 或课程 LMS 系统），通过标准协议向客户端暴露三类核心原语：
    • Tools（工具）：由模型决定调用的可执行函数（含副作用或计算操作）；
    • Resources（资源）：由应用或用户选择注入上下文的只读数据源（如文件内容、数据库记录）；
    • Prompts（提示模板）：预定义的可复用工作流提示模板。

发现与消息交换

MCP 基于 JSON-RPC 2.0 协议在运行时完成动态能力发现与调用执行：

  • 第一步：能力发现（tools/list）：当 Agent 启动或连接新服务时，Client 发送 {"method": "tools/list"} 请求，Server 返回当前可用工具的完整列表及各自的 inputSchema（例如返回 weather_current 与 calculator_arithmetic 的 Schema 及缓存有效期 ttlMs）。
  • 第二步：工具执行（tools/call）：当模型决定调用某个工具时，Client 发送 {"method": "tools/call", "params": {"name": "weather_current", "arguments": {"location": "Stanford", "units": "imperial"}}}；Server 执行后返回结构化的 content 数组（如 [{"type": "text", "text": "Current weather in Stanford: 68°F..."}]），再由 Host 交回给模型继续推理。

OpenAPI 到 MCP 与双向凭据

在工程落地中，我们可以利用 FastMCP 等工具直接将现有的 REST OpenAPI 规范（openapi.json）一键转换为 MCP Server（例如将课程系统的 GET /assignments、GET /submissions、POST /grade 自动映射为 list_assignments、get_submissions、post_grade 工具）。

在构建此类中间件服务时，必须严格区分入站鉴权（Inbound Auth）与出站鉴权（Outbound Auth）的安全边界：

PYTHON
import os, httpx
from fastmcp import FastMCP
from fastmcp.server.auth.providers.jwt import StaticTokenVerifier

# 1. 出站凭据（Outbound：MCP Server → 后端 LMS REST API）
api = httpx.AsyncClient(
    base_url="https://lms.stanford.edu/api/v1",
    headers={"Authorization": f"Bearer {os.environ['LMS_TOKEN']}"}
)

# 2. 入站凭据（Inbound：Agent Client → MCP Server）
who_may_call = StaticTokenVerifier(
    tokens={os.environ["AGENT_TOKEN"]: {"client_id": "ta-agent"}}
)

mcp = FastMCP.from_openapi(
    openapi_spec=spec, client=api, name="Course MCP", auth=who_may_call
)

为什么必须分离这两枚 Token？AGENT_TOKEN 用于验证“哪个 Agent 有权调用这台 MCP Server”；而访问底层数据库或后端 LMS 的高权限 LMS_TOKEN 则被严格封存在 MCP Server 内部，绝不暴露给大模型或 Agent 上下文。这样即便 Agent 遭遇提示注入攻击，攻击者也无法从模型上下文中窃取后端系统的主密钥，且 MCP Server 可以在转发请求前强制执行细粒度的权限审计。

4. 评测与常见故障

BFCL

我们该如何系统评测一个模型的工具调用能力？伯克利提出的 BFCL（Berkeley Function-Calling Leaderboard，Patil et al., 2025） 构建了涵盖 Python、Java、JavaScript、SQL 等多语言的综合评测体系，重点考察三个递进维度：

  1. 基于 AST 的离线结构评估：无需真实执行外部 API，直接通过抽象语法树比对模型生成的函数名、参数名与参数类型是否精准匹配；
  2. 基于真实执行的评估：实际运行函数调用，检验返回结果是否正确；
  3. 复杂场景覆盖：
    • 多函数选择（Multiple Functions）：从多个相似候选函数中选出正确的一个（如在 add 和 mult 中为 "2 + 3" 选择 add(a=2, b=3)）；
    • 并行函数调用（Parallel Functions）：单步同时发出多个独立调用（如面对 "What is (2+3) and (4+5)?" 同时生成 add(a=2, b=3), add(a=4, b=5)）；
    • 相关性检测与拒答（Relevance Detection / Irrelevance）：当用户问 "What is 2 * 3?" 但上下文中只提供了 add(a, b) 工具时，优秀的模型应当明确拒绝调用并指出缺少乘法工具，而不是强行乱调 add。

ToolBench

针对成千上万个真实 API 的组合场景，ToolBench（Qin et al., 2023） 重点评估模型在多步工具链中通过 API 检索器查找工具、阅读陌生 API 文档并完成跨领域组合调用（Multi-tool Composition）的能力。

τ-bench

然而，在 BFCL 和 ToolBench 中，用户的指令往往是一次性完整给出的。而在真实的客服、机票改签或电商售后场景中，用户最初的请求往往信息不全，Agent 必须一边与用户多轮对话收集信息，一边查阅公司政策文档，一边调用后端数据库工具修改系统状态。

τ-bench（Tool-Agent-User Interaction Benchmark, Yao et al., 2024） 正是为此设计的交互式基准：由大模型扮演具有特定诉求的用户，Agent 必须在多轮对话中同时满足两点——（1）最终将后端数据库的真实状态修改为与目标完全一致；（2）全过程严格遵守领域业务政策（例如“特价机票起飞前 24 小时内不可免费退票”）。

pass@k 与 pass^k

在 τ-bench 的评测中，研究者提出了一对极具启发性的可靠性指标对比——pass@k 与 passk（设对同一任务独立运行 n 次试验，其中成功了 c 次）：

  • pass@k（k 次尝试中至少成功 $1$ 次的概率）：
    pass@k = 1 - (n - ck)(nk)

    它衡量的是模型的探索上限（Exploration Potential），适用于代码竞赛或有外部单元测试兜底的场景——只要试 10 次能撞对 1 次就算成功。

  • passk（连续 k 次尝试全部成功的概率）：
    passk = (ck)(nk) ≈ (cn)k

    它衡量的是系统的生产级可靠性与一致性（Reliability & Consistency）。在面向真实用户的客服、金融或医疗 Agent 中，用户不可能容忍“试 8 次才成功 1 次”。实验表明，许多在单次 pass@1 上得分尚可（如 60%）的 Agent，一旦考察连续 8 次不出错的 pass8，成功率便暴跌至不足 25%。

故障范围典型失败模式具体表现与防护重点
单次调用层（Single Call）1. 工具误选（Selection）
