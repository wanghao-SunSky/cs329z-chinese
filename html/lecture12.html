第 12 讲｜数据选择与质量

在构建和优化 Agent 系统时，一个常见的误区是盲目崇拜“数据规模”：认为只要往训练集里塞进十万条自动抓取的轨迹，或者往评测集里堆砌几千道自动生成的题目，系统就能自动变强。

事实恰恰相反。在优化阶段，一千条充斥着冗余试探、格式瑕疵或偶然蒙对的低质量轨迹，不仅会拖慢训练与提示搜索速度，还会教会模型错误的行为习惯（正如 LIMA: Less Is More for Alignment 所揭示的：少量极高质量、覆盖广泛的精选示范，效果远胜海量粗糙数据）；而在评测阶段，如果测试集里 90% 都是毫无区分度的简单重复题，或者评分器本身与人类判断背道而驰，那么再庞大的基准也只是虚假繁荣。本讲聚焦于 数据选择与质量工程（Data Selection & Quality），探讨如何筛选出信息量最大（Maximally Informative）的高价值样本、如何构建小而精的靶向诊断基准（Tiny-but-targeted Benchmarks）、如何制定严密的标注规范并校准“验证器的验证器（Who Validates the Validators）”，以及如何像 SWE-smith 一样从真实软件环境中规模化合成并严格筛选高质量 Agent 轨迹数据集。

学习目标

  • 理解什么是对系统优化与评测具有最大信息量（Maximally Informative）的数据，掌握基于可验证性、多样性、难度梯度与失败模式的筛选策略。
  • 掌握构建“小而精”靶向基准（Tiny-but-targeted Benchmarks）的方法与适用边界，实现快速开发迭代与全量验收的配合。
  • 掌握高质量数据标注规范（Annotation Practices）与质量评估体系，学会使用一致性指标与分歧对齐流程校准人类标注者与自动评分器。
  • 深入理解如何从原始 Agent 运行轨迹（Traces）与代码仓库（如 SWE-smith 管线）构建大规模、经受过执行验证的训练与评测数据集。

知识讲解

1. 信息量与筛选

Maximally informative data

什么样的数据对改进或评估一个 Agent 系统“最有信息量（Maximally Informative）”？我们可以从区分度（Discriminative Power）与边界覆盖（Boundary Coverage）两个维度来界定：

  • 如果一道题过于简单，无论是零样本小模型、未优化的工作流还是精调后的 Agent 全都能拿 100% 满分，这道题提供的区分信息量为零（它只能作为防退化的基础冒烟测试）；
  • 如果一道题由于指令缺失关键信息或环境依赖损坏，导致包括人类专家在内的所有系统全部得 $0$ 分，它同样不提供有效的能力区分信息；
  • 真正高信息量的样本，位于系统当前能力边界的“最近发展区（Zone of Proximal Development）”：比如在多次采样（Repeated Sampling）中成功率在 20% \sim 80% 之间波动的任务、能够精准暴露某类典型故障模式（如新旧政策冲突、多跳中间实体消歧、工具报错后的回退恢复）的样本，或者两个候选架构方案给出截然不同结果的争议样本。

Filtering and selection

面对收集到的海量原始数据或合成候选集，工程上需要建立一套多级漏斗式的过滤与精选流水线（Filtering & Selection Pipeline）：

  1. 格式与完整性过滤（Syntactic & Structural Filtering）：剔除截断输出、JSON 语法损坏、缺失关键环境元数据或出现死循环超时的残缺轨迹。
  2. 执行结果与可验证性过滤（Execution & Verifiability Filtering）：只保留那些在确定性环境或单元测试验证器下确实达成目标的轨迹作为正样本；同时进一步检查其过程合理性——剔除那些虽然最终答案蒙对了、但中间根本没有读取关键证据文档（Citation Support 缺失）或依赖了未授权捷径的“伪成功轨迹”。
  3. 语义与轨迹去重（Semantic & Trajectory Deduplication）：不仅对用户输入的 Prompt 做 Embedding 聚类或 MinHash 去重，还要对调用的工具组合序列（Tool Call Signatures）进行分桶均衡，防止数据集中 80% 都是单一工具的简单调用，而复杂的多工具协同样本寥寥无几。
  4. 难度分层与课程采样（Difficulty Stratification）：按所需推理跳数、涉及工具数量或基准模型的通过率将样本划分为简单、中等、困难三档，按比例均衡抽样。

Tiny-but-targeted benchmarks

在日常研发迭代中，如果每次修改一行提示词或调整一个上下文压缩参数，都要跑一遍耗时 4 小时、花费 200 美元的 2,000 道全量基准题，工程迭代速度就会被彻底拖垮。

因此，高效的 Agent 团队都会维护两套互补的评测集，其中用于高频迭代的正是 小而精的靶向基准（Tiny-but-targeted Benchmarks / Micro-benchmarks）：

  • 靶向切片（Targeted Slices）：针对特定薄弱环节（如“相对日期换算”、“超大终端输出截断”、“跨会话记忆覆写”），每个切片精选 10–30 道极具代表性的高信息量样本。修改哪个模块，就在几分钟内快速跑对应切片（如同 HW1 中使用 --only memory 或 --slice 3 进行开发调试）。
  • 统计代表性压缩（如 tinyBenchmarks, Polo et al., 2024）：利用项目反应理论（Item Response Theory, IRT）分析历史大模型在全量基准上的得分矩阵，挑选出最具代表性的极少数核心题目（如从上千题中选出 50–100 题）并赋予加权系数，从而以低于 5% 的计算成本高精度逼近全量基准排序。
  • 使用边界：微型基准是开发阶段的“快速听诊器”，但绝不能为了刷高微型基准分数而针对那十几道题写硬编码规则；最终合入主干前，依然要在未参与日常调优的完整留出集（Hold-out Set）上做全量验收。

2. 标注与质量

Annotation practices

无论是构建金标准测试集，还是为训练奖励模型/评判器准备人类偏好数据，数据标注的上限取决于标注规范（Annotation Guidelines & Rubrics）的清晰度。在组织 Agent 数据标注时，应当遵循四步工程实践：

  1. 将笼统印象拆解为原子判据（Atomic Criteria）：不要让标注者笼统地给一条长轨迹打 1–5 分，而是拆解为具体的二元核对项（例如：“回答是否包含了正确的报销上限金额？”、“是否引用了 2026 版现行文档而非 2024 版旧文档？”、“在参数缺失时是否主动询问了用户？”）。
  2. 先做小规模试标与分歧复盘（Pilot Annotation & Adjudication）：先让多位标注者（包括系统构建者自己）独立标注同一批 20–30 条样本，计算标注者间一致性（Inter-Annotator Agreement, IAA，如 Cohen's κ 或 Krippendorff's α）。
  3. 分歧往往意味着规格缺陷：当两位认真的标注者对同一条轨迹给出相反判定时，通常不是因为标注者粗心，而是因为题目要求或评分准则存在未定义的灰色地带（比如“邮件里只写了下周三，按发出时间算还是按今天算？”）。必须把消除分歧的边界判例补充写回标注指南中。
  4. 保留“无法判定 / 题目有误”出口：允许标注者标记某道题目本身环境损坏或存在歧义，及时将坏题踢出数据集。

Quality assessment

当我们用大语言模型辅助数据标注或充当自动化裁判（LLM-as-Judge）时，一个核心问题是：谁来检验验证器本身是否靠谱（"Who Validates the Validators?", Shankar et al., 2024）？

评估数据集与自动评分器的质量需要建立双向对齐机制：

  • 真阳性率（TPR / Sensitivity）与真阴性率（TNR / Specificity）：构建一批人工确认无误的黄金正负样本集，分别测量自动评分器在多大比例上将真实好样本判为 PASS（TPR）、将真实坏样本判为 FAIL（TNR），而不是只看一个容易被类别不平衡掩盖的总体准确率；
  • 人机动态协同对齐（Human-LLM Alignment Loop）：正如 Shankar et al.（2024）在 EvalGen 系统研究中所揭示的，人类的评判标准并非在写提示词那一刻就完全定型的，而是在看到模型各种千奇百怪的实际输出后才逐步明确起来的（Criteria Drift）。因此，必须通过交互式界面让工程师审查自动评分器的判例、发现漏判模式并迭代修正评分标准。

从 Agent traces 建数据集

如何将上述原则结合起来，构建能够支撑现代编程与工具 Agent 训练的工业级数据集？斯坦福团队提出的 SWE-smith（Yang et al., 2025，《Scaling Data for Software Engineering Agents》） 展示了如何突破真实人工标注瓶颈，从开源代码仓库规模化构建经过严格执行验证的 Agent 任务与轨迹数据集：

  1. 构建统一可执行的仓库环境（Environment Construction）：收集真实的 Python 开源代码仓库，自动配置可复现的 Docker 容器環境并确保其原有的单元测试套件能够 100% 跑通；
  2. 反向合成真实感 Bug（Task / Bug Synthesis）：与其苦苦搜寻历史上恰好附带完整测试的少量真实 GitHub Issues，SWE-smith 反其道而行之——在已经跑通测试的健康代码库上，利用大模型对函数或类实施受控修改（或回滚历史提交），只要该修改导致现有测试套件中至少一个单元测试由绿变红（Fail），就成功合成出了一个百分百可验证的软件修复任务！随后再由模型根据损坏的代码与报错堆栈生成自然语言 Issue 描述；
  3. 大规模轨迹采样与执行过滤（Trajectory Rollouts & Verification）：让强模型 Agent 在这些合成出的数万个 Bug 任务容器中进行多步探索与修改，凡是最终生成的补丁（Patch）能够让全部单元测试重新由红变绿（Pass）的运行轨迹，即被收录为高质量的成功训练轨迹；
  4. 仓库级严格隔离（Repository-level Split）：在划分训练轨迹与 SWE-bench 评测集时，严格保证训练集中的代码仓库与测试集仓库零重叠，杜绝数据泄漏。

通过这套“真实环境 + 反向造题 + 单元测试硬核过滤”的管线，SWE-smith 生成了数万条高质量软件工程轨迹，使开源小模型在微调后获得了大幅的真实仓库修复能力跃升。

原课程阅读清单与导读

  • Yang et al. "SWE-smith: Scaling Data for Software Engineering Agents." NeurIPS D&B (2025). 导读：重点阅读如何通过反向注入破坏单元测试的修改来合成无限量的可验证编程任务，以及如何过滤 Agent 采样轨迹用于模型微调。
  • Shankar et al. "Who Validates the Validators? Aligning LLM-Assisted Evaluation with Human Preferences." UIST (2024). 导读：理解“标准漂移（Criteria Drift）”概念——为什么用户在看到真实模型输出前很难一次性写全评价标准，以及如何对齐代码/LLM 断言与人类判断。
  • 拓展阅读：Zhou et al. "LIMA: Less Is More for Alignment." NeurIPS (2023). 导读：思考在微调与示范选择中，为什么 1,000 条精心挑选、风格一致且推理严密的样本能够击败数万条未经筛选的嘈杂数据。

动手练习

  1. 高信息量诊断切片构建：从 HW1 的邮件问答（email_qa）与文档检索（search_docs）任务出发，设计一个仅包含 6 道题的微型靶向诊断集（Micro-benchmark），分别精准测试：（a）单跳精确词匹配、（b）两跳跨邮件人员关联、（c）被新政策废止的旧政策干扰、（d）词面无重叠的同义改写查询、（e）文档中夹带提示注入指令、（f）问题本身所问信息在库中不存在。为每道题写明入选理由与期望的标准行为。
  2. 标注一致性与评分器校准实验：针对上述 6 道题，编写一套包含 3 条原子判据的评分量表（Rubric），构造 10 份包含微妙缺陷的候选回答（例如数值算对但引用了旧文档 ID、或回答正确但多输出了一句无关推测）。分别用你编写的 LLM-as-Judge 提示词和人工盲评对这 10 份回答打分，计算真阳性率（TPR）与真阴性率（TNR），并针对分歧案例修改 Judge 提示词。
