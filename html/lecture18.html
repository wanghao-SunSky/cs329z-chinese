第 18 讲｜主动式 Agent

到目前为止，我们在课程中讨论的几乎所有 Agent——无论是问答助手、RAG 流水线还是处理工单的编程 Agent——都遵循着同一种交互模式：被动响应式（Reactive）。如果你不向它发消息，它就永远安静地停在那里；只有当你明确敲下指令、点明要做什么，它才会启动循环去执行。

然而，真正得力的人类搭档绝不会事事等你开口下令。当你正在撰写一份季度总结文档、反复在邮件和表格之间切换查核数据时，一位默契的搭档会注意到你的意图，主动帮你把最新一周的销售表格整理好放在手边；当你收到一封重要会议改期的邮件时，他会主动提醒你这与周四的航班冲突，并为你拟好改签建议草稿等你确认。

从“你问一句，我动一下（Reactive）”走向“理解你的上下文与长远目标，在恰当时机主动提供协助（Proactive）”，是个人与企业 AI Agent 演进的下一个重大前沿。本讲将深入剖析 主动式智能体（Proactive Agents） 的核心技术体系：探讨如何从日常计算机交互中构建通用用户模型（General User Models, GUM）、如何进行下一步动作预测（Next Action Prediction）、剖析开源主动式个人 Agent（如 OpenClaw）的常驻架构，并深入研究持续观测带来的隐私信任挑战以及决定“何时该主动出手、何时该安静等待”的混合主动权（Mixed Initiative）决策机制。

学习目标

  • 理解被动式智能体（Reactive Agents）与主动式智能体（Proactive Agents）的本质区别，认识主动性带来的生产力解放与干扰风险。
  • 掌握通用用户模型（General User Models, GUM）如何从多模态计算机交互日志中归纳用户的知识状态、偏好与当前目标。
  • 理解基于人机交互序列的下一步动作预测（Next Action Prediction），严格区分“预测用户下一步会做什么”与“Agent 获准替用户执行什么”。
  • 剖析开源常驻主动式 Agent（如 OpenClaw）的心跳唤醒（Heartbeat）、多通道网关与夜间记忆整理机制，掌握混合主动权（Mixed Initiative）的效用—打扰权衡与隐私边界设计。

知识讲解

1. 从 reactive 到 proactive

Reactive 与 proactive

将响应式 Agent 与主动式 Agent 放在系统层面对比，两者的触发机制与认知负担截然不同：

维度被动响应式智能体（Reactive Agents）主动式智能体（Proactive Agents）
触发起点仅由用户的显式指令（Explicit User Prompt）触发由环境事件、时间周期、上下文状态变化或观测到的用户行为流自主触发
意图发现责任完全落在人类用户肩上（用户必须自己发现问题并把需求组织成清晰的提示词）由 Agent 与用户分担（Agent 持续感知上下文，识别潜在需求、冲突或可自动化的重复劳动）
主要失败模式答非所问、工具调用失败、执行超时误触发打扰（False-positive Interruption）、自作主张引发错误副作用、过度窥探造成隐私不安
核心评测指标给定指令下的任务完成率（Pass Rate）、成本与延迟建议采纳率、为用户节省的操作步数、打扰率（Interruption Rate）与撤销成本

为什么在很多场景下仅靠 Reactive 是不够的？因为人类用户在专注工作时，往往存在三重障碍：（1）不知道某件繁琐的事其实可以让 Agent 自动化处理；（2）把复杂上下文用文字敲成提示词解释给 AI 听的功夫，还不如自己顺手干完（即提示规范开销 Prompting Overhead）；（3）对于日程冲突、后台报警或即将到期的截止日，用户自己根本还没注意到，自然不可能主动去问 AI。

General User Models（GUM）

要让一个 Agent 能够恰到好处地主动帮忙，前提是它必须先真正“懂你”——知道你正在忙什么项目、习惯什么样的工具流程、认识哪些合作者、有哪些未完成的待办事项。

斯坦福团队提出的 通用用户模型（General User Models, GUM, Shaikh et al., 2025，《Creating General User Models from Computer Use》） 开创了从日常多模态计算机使用行为中自动构建结构化用户表征的范式：

  1. 多源交互观测（Multimodal Computer Use Observation）：系统在本地受控环境下观测用户在操作系统中的日常交互（如屏幕截图变化、活跃窗口切换、文档编辑与网页浏览轨迹）；
  2. 结构化命题归纳与置信度更新（Propositional User State）：GUM 不是简单地把几万张截图存进向量库，而是通过视觉—语言模型从交互流中持续提炼、更新关于用户的结构化命题（Propositions，例如“用户正在准备 CS329Z 的期中项目报告，重点关注 RAG 评估指标”、“用户习惯使用 uv 而非 pip 管理 Python 环境”），并为每条命题维护置信度、证据来源与时效衰减；
  3. 跨应用泛化赋能：一旦建立起动态更新的 GUM，任何下游应用或 Agent 在启动时无需用户从零交代背景，即可直接查询 GUM 获得高精度的个性化上下文，不仅能够补全模糊指令中的指代，还能主动发现跨应用的工作流衔接机会。

Next Action Prediction

有了对用户当前状态的理解，主动式 Agent 的下一个核心计算问题是 下一步动作预测（Next Action Prediction, Shaikh et al., 2026，《Learning Next Action Predictors from Human-Computer Interaction》）：给定用户过去一段时间的交互历史序列 (s1, a1, s2, a2, …, st)，预测用户接下来最可能执行的操作 at+1 或高层次意图。

在工程实现中，必须清醒把握一条关键原则：“准确预测出用户下一步想干什么”绝不直接等同于“Agent 应当立刻替用户把这一步干掉”！

  • 如果预测出用户正在把一封邮件里的 10 个日期逐个复制到表格里，主动帮他生成填好后 8 行的预览供他一键确认（Autocomplete / Draft），是极佳的体验；
  • 但如果预测出用户看完了邮件准备点击“发送辞职信”或“合并生产分支”，Agent 绝不能不打招呼就直接替用户点下去。预测模型提供的是意图先验（Intent Prior），而真正决定采取什么介入动作的，是上层的主动决策策略（Initiative Policy）。

开源主动个人 Agent

在开源工程界，以 OpenClaw（Steinberger, 2025） 为代表的常驻型个人 Agent 展示了如何用简洁的工程组件搭起一套 7×24 小时运转的主动式系统（我们在第 05 讲曾简要见过其身影）：

  1. 单一长驻网关进程（Long-lived Gateway）：不再是每次打开网页才初始化的临时会话，而是一个常驻后台的服务进程，统一接管用户的消息通道（如 Telegram、Slack、邮件通知与本地目录监听）；
  2. 基于定时心跳的主动轮询（Scheduled Heartbeat Turns）：系统每隔固定周期（如每 30 分钟）自动触发一次隐式的“心跳轮次（Heartbeat）”——唤醒 Agent 检查当前时间、近期收到的新消息、日历待办与监控列表。最关键的设计在于静默默契：如果 Agent 检查后认为当前没有任何值得打扰用户的重要事项，它只需输出特殊标记 NO_REPLY，网关会直接吞掉这次心跳，用户端完全无感；只有确实发现紧急冲突或到期提醒时，才会真正向用户推送消息；
  3. 基于 Markdown 文件的透明人格与记忆（File-based Identity & Sleep-time Consolidation）：通过 AGENTS.md、SOUL.md、USER.md 与 MEMORY.md 维护长期状态，并在每天凌晨（如 3 AM）运行后台整理任务，将当天的交互日志提炼归档。

2. 隐私、信任与 mixed initiative

Privacy and trust

主动式 Agent 的能力越强、观测的屏幕与个人数据越全面，它所触及的隐私与信任边界（Privacy and Trust Implications）就越敏感：

  • 持续观测的最小化与本地化原则：屏幕截图、键鼠记录与私人通信包含了大量高度敏感的信息（密码框、私人聊天、银行账单）。在设计类似 GUM 的持续观测系统时，应当支持应用级黑名单过滤（排除密码管理器、私人金融与医疗页面）、优先采用本地端侧模型提炼抽象命题后立即销毁原始截图，并严禁将未经脱敏的原始监测流直接上传至不可信的公共云端；
  • 可审计与可修正的透明度（Inspectability & Correctability）：用户必须能够随时打开查看“Agent 目前对我形成了哪些推断和记忆”，并能一键删除或纠正错误的推断（例如当 Agent 误以为用户对某个临时搜索过的商品长期感兴趣时，用户能直接划掉该画像条目），这是建立长期人机信任的基石。

Initiate vs wait

主动式 Agent 设计的最高艺术，在于处理 混合主动权（Mixed Initiative，Horvitz, 1999 经典人机交互理论在 LLM 时代的延续）——即在每一个时刻，系统如何在“主动发起行动（Initiate）”、“礼貌询问或提供草稿（Suggest / Ask）”与“安静等待（Wait / Do Nothing）”之间做出最优抉择。

我们可以用一个简单的期望效用决策矩阵来指导这一工程设计。设 Agent 估计当前用户确实需要某项帮助的概率为 P(Need)：

  • 如果主动出手且猜对了，能为用户带来的净收益为 Uhelp > 0；
  • 如果主动出手但猜错了（误触发），给用户造成的打扰成本与撤销/清理代价为 Cinterrupt > 0。

只有当期望收益大于期望打扰代价，即 P(Need) · Uhelp > (1 - P(Need)) · Cinterrupt 时，才值得发起主动动作！更重要的是，我们可以通过设计渐进式的介入阶梯（Graduated Spectrum of Initiative）来大幅降低误判代价 Cinterrupt：

介入等级触发条件（置信度 P 与操作可逆性）Agent 采取的具体行为误判时的用户撤销成本
Level 0：完全静默（Wait / NO_REPLY）置信度低，或用户正处于高频专注输入/会议免打扰状态后台静默记录日志，不发出任何通知或动作零打扰
Level 1：无侵入就地准备（Silent Staging / Draft）置信度中等，发现需要处理的邮件或待办不弹窗打扰用户，但在后台默默查好相关资料、在草稿箱里生成好回复草稿（Draft）或待办卡片，等用户主动打开收件箱时直接呈现极低（用户只需忽略草稿）
Level 2：轻量级主动建议（Proactive Suggestion）置信度高，或检测到迫在眉睫的日程冲突/截止日期发送一条简明扼要的通知卡片，附上已准备好的解决方案，提供 [一键确认执行] 与 [忽略] 按钮中等（消耗用户几秒钟阅读注意力）
Level 3：自主执行并事后汇报（Autonomous Action + Log）置信度极高、操作完全可逆（Reversible）且用户已预先明确授权该类规则自动完成归档、打标签或启动本地构建，并在活动日志中留存一键回滚记录仅限事先授权的低风险可逆操作

在评测主动式 Agent 时，切忌只拿正样本测试“它有没有主动提醒”。一个合格的主动式基准必须包含大量应该保持安静的日常流水样本，同时统计精确率（Precision，发出的主动打扰中有多少比例真正被用户采纳）、召回率（Recall，真正需要提醒的关键事件捕获了多少） 以及用户拒绝建议后的静默退避能力（当用户刚刚拒绝过某类建议后，绝不在五分钟后又换个花样弹出来烦人）。

动手练习

  1. 设计四级混合主动权（Mixed Initiative）策略引擎：围绕个人办公场景构造 8 个事件快照（例如：① 收到一封明天的普通推广周报；② 收到封要求周五前回复报销单的同事邮件；③ 检测到 15 分钟后有线上会议但尚未生成议程摘要；④ 用户刚刚在 2 分钟前点击拒绝了“自动整理桌面文件”的建议）。为每个事件判定应采取的介入等级（Level 0 静默 / Level 1 后台草稿 / Level 2 主动弹窗建议 / Level 3 自动执行），并写出判断依据。
  2. 实现心跳检查与防重复打扰状态机：编写一个模拟 heartbeat_check(events, memory) 的函数：当没有任何紧急新事件或某事件已在过去 24 小时内提醒过用户时，严格返回 "NO_REPLY"；当发现新的高优先级冲突时，先调用只读工具准备好上下文草稿，再生成一条不超过 100 字的精简行动建议并记录已提醒状态。
