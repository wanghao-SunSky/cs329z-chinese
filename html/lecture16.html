2. 三大支柱的工程闭环与选型矩阵

当我们面对一个真实的业务或研究问题时，切忌一上来就拉起三四个多智能体群聊或盲目微调模型权重。一个成熟的 Agent 工程师会按照以下五个递进层级做出架构选型：

决策阶段核心工程问题默认首选方案（Keep It Simple）何时升级到更复杂方案（Upgrade Trigger）
1. 控制流选型谁来决定下一步？（Workflow vs. Agent）步骤固定、分类明确的任务，优先采用 Prompt Chaining / Routing / Parallelization 等确定性工作流任务需要根据环境反馈做多轮未知探索（如排查未知代码故障、多跳动态检索）时，才引入 ReAct / CodeAct 循环
2. 知识与工具接入如何补充外部信息与行动能力？优先使用 BM25 + 稠密向量混合检索（RRF）；工具集保持极简正交（如遵循 MCP 标准协议）单次检索召回不足时升级为带跳数限制的 Agentic RAG 或引入 ColBERT / Cross-Encoder 重排
3. 上下文与记忆治理如何应对长周期与跨会话状态？维护不可变的 Event Log，结合低成本的 Observation Masking 截断陈旧巨型输出，保持前缀稳定以复用 KV Cache超出窗口预算时触发结构化 Compaction；需要跨会话延续偏好或技能时引入 Mem0 / MemGPT / Skill Files
4. 单智能体 vs. 多智能体是否需要拆分多个角色？永远先构建并压榨 强单 Agent 基线（Strong Single-Agent Baseline）仅当子任务天然可解耦并行、或需要严格的上下文隔离（Sub-agents）且实测收益大于协调成本时，才引入 Orchestrator-Workers + Task Ledger + Worktree 隔离
5. 系统优化路径如何提升最后一公里准确率与性价比？先冻结评测指标，使用 DSPy Bootstrapping / MIPROv2 / GEPA 优化少样本示范与提示词当提示优化触及天花板、或需将大模型能力蒸馏至低延迟小模型时，才开展轨迹 SFT / GRPO / 在线策略蒸馏

3. 端到端系统故障诊断树

当你的 Agent 在评测集或线上运行中出现失败时，可按照以下五步诊断树由外向内快速定位根因：

  1. 检查评测器与环境（Is the Eval Broken?）：打开完整 Transcript，确认是不是因为测试环境未重置、外部依赖波动，或者 Verifier 正则断言过于死板（False Negative）冤枉了合理的解法。
  2. 检查感知与检索层（Did it Find the Right Context?）：如果答案错误，先看所需的正确文档或邮件是否出现在了 search 工具的返回结果中（排查检索端 Recall Ceiling），还是虽然检索出来了却因上下文太长被模型忽略（排查阅读端 Lost in the Middle）。
  3. 检查工具契约与执行层（Did the Tool Call Succeed?）：检查是否存在 JSON 协议截断、参数类型不匹配、或是工具返回了不透明的错误码导致模型在同一条失败命令上死循环重试。
  4. 检查长程状态与记忆层（Did Context Drift or Conflict Occur?）：在 10 轮以上的长任务中，检查是不是 Compaction 摘要丢掉了第 1 轮的用户硬约束，或者是跨会话记忆同时返回了相互矛盾的新旧数据。
  5. 检查安全与人机边界（Did it Violate Policy or Act Without Clarifying?）：检查 Agent 是否在信息模糊时盲目猜测而非调用 ask_user，或者是否被外部文档中的间接提示注入带偏了执行方向。
